## DESIGN

1. Add typed `prompts_disabled` boolean per upstream server, default false; strict allow-list and typed-field validation reject unknown keys/types. Include it in config identity/fingerprinting and staged reload. Disabled servers bypass prompt discovery and are absent from prompt registry; change applies only upon successful staged config replacement.
2. During the same refresh pass as tools, query upstream InitializeResult capabilities, then use paginated `Prompts` or equivalent cursor loop. Treat each server's prompt page walk as all-or-error; sort by raw name and reject nameless entries/non-advancing cursors. Preserve per-server isolation: prompt failure marks that server's prompt contribution stale/unavailable and retains its own LKG set; healthy servers publish. A fresh successful empty list is a valid removal.
3. Store prompts in a **separate durable prompt object**, not in the existing tool snapshot: a sibling object with its own format version, checksum, atomic temp-write/fsync/rename publication, and strict decode/reconcile. Keep existing tool snapshot bytes, version, checksum, and decode/validation path unchanged. Load and validate the tool snapshot independently; then independently load the prompt object. A missing prompt object means empty prompts on first install, or prompt unavailable/stale when prompt state was expected; it never prevents tools loading. Publish tool and prompt candidates independently: a prompt-object write/rename failure leaves the last valid prompt object and prompt registry intact while a successfully published tool snapshot remains active; a tool publish failure leaves its prior tool snapshot active while an independently successful prompt publication may proceed only against the still-active server/config identity. Never publish a mixed candidate based on an uncommitted reload. Each component retains its own last-known-good state and status.
4. Derive opaque public names deterministically from canonical JSON `[server_id, raw_name]`, using a prompt-specific prefix/domain separator so prompt identifiers cannot collide with tool identifiers. Carry server ID and raw upstream name only in provenance metadata/description and internal mapping; never expose raw name as wire identifier. Preserve prompt title/description/argument schema where protocol permits, adding provenance without replacing upstream meaning. Detect derived-name collision and reject ambiguous publication rather than route nondeterministically.
5. Reconcile SDK native server registration using AddPrompt/RemovePrompts after atomic publish; handler closes over immutable published mapping. `prompts/list` returns current public definitions with pagination compliant with SDK. `prompts/get` maps public name to exactly one upstream server/raw name and forwards arguments exactly once. No retry/re-dispatch; enforce existing per-server deadline/concurrency/breaker boundaries. Map upstream errors to safe generic protocol errors with correlation-safe logs; never return raw transport/upstream error strings. Unknown public name uses invalid-params/unknown-prompt behavior.
6. Force advertised inbound `prompts{listChanged:true}` on cold start via verified SDK `HasPrompts`/Capabilities option; do not wait for first registration. Notifications occur only on published prompt-set changes, including removals, and must not trigger tools `catalog_changed` or bump tool revision.
7. Use bounded metrics only: add finite `prompts_list` operation/outcome values to existing request metric if cardinality remains bounded; add prompt count gauge without prompt/server labels. Do not create a new listener or observability subsystem.
