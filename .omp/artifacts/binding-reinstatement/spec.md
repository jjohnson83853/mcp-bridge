## 8. RELEASE AND RECOVERY

In-process behavior change; no schema/config/wire change; no migration; no storage-protocol change; **the shutdown-ordering fix (cancel-before-await, join, unconditional close) makes the recovery paths race-free AND removes the 10 s listener-failure hang.** Deployment: standard rollout; the first committed admission reinstates (one warn per reinstated server); `prompts.json` purged on the reinstatement path; the first startup prompt write prunes unconfigured/prompt-disabled rows (disclosed). **Rollback and failure recovery (the two-class contract):**
- **PRE-RENAME failures: the binding STAYS RETIRED; the previous binary hits the ORIGINAL refusal (`reconcile.go:80-81`) — the crash-loop RESUMES until the new binary retries successfully or the owner lane repairs the state; retries are idempotent; the eventual successful retry emits exactly one record per reinstated server.**
- **POST-RENAME/FSYNC failure (ADR15): rejected admission, no record, on-disk state UNCERTAIN. Rollback compatibility DEPENDS ON THE SURVIVED BRANCH: survived — the previous binary reads/validates the non-retired snapshot and starts without crash-loop (startup: empty catalog until first probe; reload with successful discovery: current-era rows restored via the OLD binary's startup `definitionsFromSnapshot` path, `:901`); not survived — the tombstone remains and rollback resumes the crash-loop. - **Commit-point emission guarantee: a `binding_reinstated` record exists ONLY for a reinstatement whose snapshot persist returned success and whose runtime generation was accepted — one per reinstated server, startup/reload only (the guard).**
