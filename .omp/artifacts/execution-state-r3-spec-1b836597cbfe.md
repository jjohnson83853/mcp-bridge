# Header Parameter Transit — Header-Annotated Tool Parameters Through the Bridge (SpecDD, feature `header-parameter-transit`)

## 1. STATUS

Spec ID `header-parameter-transit`, revision r3. State: **DRAFT** (revised after review; no execution authorization). Objective: make a `tools/call` for a tool whose published input schema annotates parameters with `x-mcp-header` reach an upstream that negotiated protocol `2026-07-28` or later, in the default `stateless: true` configuration, without pinning a session and without weakening restart resilience; make the explicit-stateful path and the legacy-protocol boundary deterministic and named. Evidence scope: backlog MB-001, tickets `issues/01`–`issues/04`, and the source anchors in §3. Revision history: r1 (initial); r2 (CR1 **REQUEST CHANGES**, findings F1–F6: legacy peer pinned to `2025-11-25` with its verified fallback path in T1 and AC03-2, T2 command 2 bounded to feature oracles plus the two designated regression tests, AC02-2 and AC03-2 counting scope pinned to the peer-observed `tools/list` total inside the `5m` refresh window, header-emission wording qualified to a session negotiated at `>= 2026-07-28`, anchors corrected to `config.go:42-53` and `logging-contract.md:312-320`, last-completion publication sentence corrected, and warm cost stated as `k+1` list RPCs in the paginated worst case); r3 (CR2 **REQUEST CHANGES**, H1 and L1–L3: the modern test peer is now built as a *stateless* streamable handler, because the server transport refuses `>= 2026-07-28` unless stateless and a stateful handler silently negotiates `2025-11-25`, which would make AC01-2/AC01-4/AC02-1/AC03-1 unattainable; anchors repointed to `config.go:41`, `core.go:245-262` and `runtime.go:184-233`, the restart-harness range narrowed to `:155-218`, and the focused `-run` patterns widened with `HeaderParameter` so the AC03-1 and AC03-2 oracles actually run). ## 2. REQUIREMENTS
<!-- specdd:requirements:start -->
**R1 (default stateless transit).** With default configuration (`stateless` unset ⇒ true, `internal/config/config.go:48-53`), a `tools/call` for a tool whose last successful discovery published an input schema containing an `x-mcp-header` annotation MUST reach the upstream as one execution whose outbound request carries the parameter values both in the JSON `arguments` and in matching `Mcp-Param-<Header>` request headers. No upstream session may be retained between calls to achieve this.

**R2 (definition source, single emitter).** The bridge MUST NOT construct, encode, re-encode, or strip `Mcp-Param-*` headers itself. Emission MUST be the go-sdk client's, driven by the tool definition present in the executing session's `tools/list` cache. The bridge's only responsibility is to ensure that definition exists on the execution session for tools it knows to be header-bound. Per-parameter selection and value encoding are therefore the SDK's SEP-2243 rules, not a second bridge-local implementation.

**R3 (control preservation).** A tool with no `x-mcp-header` annotation MUST behave exactly as today: no additional upstream RPC, no additional header, identical arguments bytes and identical result content.

**R4 (argument retention).** Header-bound values MUST remain in the JSON `arguments` object, byte-preserved through the existing decode/encode path, and the headers MUST be additive. Removing a value from `arguments` is prohibited because the SDK peer validates header/body agreement and rejects a header whose body parameter is absent (see §3).

**R5 (explicit stateful mode).** With `stateless: false`, a header-bound tool MUST succeed using the definitions cached by discovery on the runtime's single cached session, with no extra session and no eviction.

**R6 (legacy boundary).** When the executing session negotiated a protocol version lower than `2026-07-28` and the tool is header-bound, the bridge MUST answer with the named, payload-free failure code `parameter_header_unsupported` and execution state `not_started`, with **zero** upstream tool executions, **zero** `tools/list` warm request, and no breaker mutation. It MUST NOT answer with `tool_reported_error` or `upstream_protocol_error`, and it MUST NOT reject discovery (which would remove working non-header tools on the same server).

**R7 (documented boundary).** Repository documentation MUST state which protocol versions carry parameter headers, how the bridge behaves in stateless and stateful mode, the exact failure code for older upstreams, and the operator action required.

**R8 (payload-free failure vocabulary).** Every failure path on the header call path MUST be payload-free (no tool names, argument values, header values, URLs or tokens in messages) and MUST use the existing safe code set, except for the single additive reason token in R6, which MUST be registered consistently in the closed runtime reason vocabulary, the client-facing dispatch code, and the logging contract. No new log event name, field name, metric family, or metric label is permitted.

**R9 (deterministic reproduction).** A test that drives the bridge's own Tool server against a controllable peer MUST reproduce the defect and record the negotiated protocol version, the presence or absence of each parameter header, and the outbound arguments body, in both default stateless and explicit stateful mode, with no dependency on the live github upstream.

**R10 (deployed verification).** The shipped build MUST be verified on the live deployment against the github upstream: the header-bound call returns content, the query-only control succeeds in the same window, and structured logs for the header call show no `tool_reported_error` and no `upstream_protocol_error`. This requirement is operator-gated and outside the code envelope.

**R11 (restart resilience).** `TestUpstreamRestartSurvivesInDefaultStatelessMode` MUST pass unchanged in meaning: a stateless header call must still open a fresh session and survive an upstream generation swap with a subsequent successful call.

**Non-goals.** No configuration key, default change, or `stateless` policy change; no session pinning, session eviction, or reconnect policy; no go-sdk upgrade or vendored patch (stays v1.8.0); no change to `core.Upstream`, `core.Bridge.Dispatch`, catalog publication, search/embedding, the breaker state machine, metrics, capacity or readiness; no new log event/field, metric family or label; no retry/replay of an upstream call; no transport-header workaround (a bridge-side `RoundTripper` emitter) and no build-tag or protocol-patch hack; no change to the upstream server's own protocol implementation.

## 3. EVIDENCE AND UNCERTAINTY

### VERIFIED (source-anchored)

- **Default is stateless.** `Server.Stateless *bool` at `internal/config/config.go:41`; `ServerStateless()` returns true when nil and the predicate spans `internal/config/config.go:48-53`. The bridge's upstream facades are built from that predicate (`cmd/mcp-bridge/wiring.go:145-209`, `Server: options, Stateless: server.ServerStateless()`).
- **Stateless discovery opens and closes a session.** `Dedicated.Discover` connects, records the negotiated version for the ephemeral-handshake log and for the legacy flag, paginates `ListTools`, then closes the ephemeral session; stateful discovery reuses `sessionFor` (`internal/upstream/dedicated.go:71-148`, `:294-310`). The same function already compares the session's `InitializeResult().ProtocolVersion` against `2026-07-28`, so the negotiation fact the legacy gate needs is already read on that path.
- **Stateless execution opens a fresh session and never lists tools.** `Dedicated.CallTool` connects, optionally logs the ephemeral handshake, decodes the arguments, and performs exactly one `d.client.CallTool` (`internal/upstream/dedicated.go:359-415`, call at `:401`). There is no `ListTools` on the execution session.
- **The SDK client caches tool definitions only as a side effect of its own `ListTools`, and only under the new protocol.** `ClientSession` holds a per-session `toolsCache`; `ListTools` consults it and stores the result only when `usesNewProtocol()`; `CallTool` looks the tool up with `lookupTool` and injects it into the request context (`go-sdk v1.8.0` module file `mcp/client.go`, symbols `usesNewProtocol`, `toolsCache`, `lookupTool`, `ListTools`, `CallTool`).
- **`usesNewProtocol()` is a version comparison.** It is true when the initialize result's `ProtocolVersion` is `>= 2026-07-28` (`go-sdk v1.8.0` `mcp/client.go`).
- **Header emission requires both the cached definition and a session negotiated at `2026-07-28` or later.** On the client, the transport sets `Mcp-Protocol-Version`, and only on a session negotiated at or above `2026-07-28` does it call `setStandardHeaders`; below that version it returns without setting any standard header. On a qualifying session that function sets `Mcp-Method` for every request, sets `Mcp-Name` whenever the method carries an extractable name, and for `tools/call` emits `Mcp-Param-<Header>` from `generateParamHeaders` when the tool is in the request context. A `tools/list` on such a session therefore also carries `Mcp-Method`, so the warm request is a compliant new-protocol request (`go-sdk v1.8.0` `mcp/streamable.go`, `mcp/streamable_headers.go`, `minVersionForStandardHeaders`). The server side mirrors the same boundary: `StreamableServerTransport.SupportsProtocolVersion` returns true for a version at or above `2026-07-28` only when the transport is stateless (`go-sdk v1.8.0` `mcp/streamable.go:871-876`); `Server.Connect` filters the advertised version list through that predicate (`mcp/server.go:1459`), and `server/discover` serves the filtered list (`mcp/server.go:926-929`). A stateful streamable test peer pinned to `2026-07-28` therefore advertises nothing at that version and the client falls back to legacy `initialize`.
- **Parameter encoding is SEP-2243 and primitive-only.** `generateParamHeaders` reads the annotations from the definition's `InputSchema`, reads `arguments`, skips absent and `null` values, and encodes only string, bool, and safe-range integer primitives; anything else yields no header (`go-sdk v1.8.0` `mcp/streamable_headers.go`, `generateParamHeaders`, `primitiveToString`, `unmarshalPrimitive`, `encodeHeaderValue`).
- **The SDK peer enforces header/body agreement.** `validateMcpHeaders` applies at or above `minVersionForStandardHeaders`; `validateParamHeaders` requires a matching `Mcp-Param-<Header>` for every annotated parameter that is present and non-null in the body (a missing header is a `header mismatch` error), requires the header to be absent when the body parameter is absent or `null`, rejects an undecodable header, rejects a header when the body value is not a primitive, and rejects a value mismatch (`go-sdk v1.8.0` `mcp/streamable_headers.go`, `validateMcpHeaders`, `validateParamHeaders`, `primitiveEqual`). This is why R4 retains the values in `arguments`.
- **A peer can pin the protocol in either direction.** `ServerOptions.SupportedProtocolVersions` narrows the advertised versions and rejects excluded new-protocol requests (`go-sdk v1.8.0` `mcp/server.go`, `ServerOptions`), so a test peer can be pinned to `2026-07-28` — but the pin takes effect only on a stateless server transport (previous bullet). Pinning an older-only list (`[]string{"2025-11-25"}`) forces the legacy path deterministically, and that path is source-verified: the client asks for the latest version, the peer's `server/discover` probe is rejected with `UnsupportedProtocolVersion` carrying its supported list, the client retries discover only for a mutually supported version at or above `2026-07-28` (`mcp/client.go:363-375`), and otherwise falls back to the legacy `initialize` at `protocolVersion20251125` (`mcp/client.go:376-381`), so the session reports `2025-11-25`, `usesNewProtocol()` is false, and no tool cache is populated.
- **The bridge has no header translation today.** `grep -r 'x-mcp-header' internal/` returns nothing; the input schema is canonicalized and published unchanged (`internal/core/core.go:245-262`, `internal/upstream/dedicated.go:107-140`); the call path forwards the client's raw arguments unchanged (`internal/service/tools.go:780`).
- **Direct execution shares the same dispatch.** Pinned/direct executions call `Dispatch` too (`internal/service/direct_execution.go:46`), so one fix covers both surfaces.
- **Admission precedes execution and slots are bounded.** `ServerClient.CallTool` applies the call timeout, admits through `AdmitCall`, and only then calls `session.CallTool`; the returned release closes the slot (`internal/upstream/runtime.go:184-233`, `:237-253`).
- **The failure vocabulary is closed and finite.** Reason tokens are listed in `internal/observe/log.go:158-167` and validated by the finite-enum path; `RuntimeErrorInfo` maps a token to kind/retryable/remediation and collapses unknown input to `unknown` (`internal/observe/envelope.go:103-133`); the client-facing result shape is `{code,message,retryable,execution_state}` with a fixed message per code (`internal/service/tools.go:1037-1064`), and discovery codes and unmapped dispatch codes degrade safely (`:1015-1034`).
- **The logging contract is partly machine-checked.** `cmd/mcp-bridge/logging_contract_test.go` compares the delimited envelope-field and diagnostic-code lists with the Go registries; the reason vocabulary appears as a documented table (`docs/logging-contract.md:312-320`), so extending it is a text edit that no test pins to an exact set.
- **Test harnesses exist, but their handlers are stateful.** `newPeer` builds a real SDK peer over the streamable transport with an opt-in `ServerOptions` and a body/request-counting wrapper (`internal/upstream/dedicated_test.go:40-59`), yet it passes a nil `*mcp.StreamableHTTPOptions` to `mcp.NewStreamableHTTPHandler` (`:45`), so its transport is stateful; `newPeerHandler` does the same (`cmd/mcp-bridge/serve_upstream_restart_test.go:29-44`, handler at `:37`). A peer that must negotiate `2026-07-28` therefore has to be built with `&mcp.StreamableHTTPOptions{Stateless: true}` in the new test file. `newPeerHandler` and `startUpstreamRestartBridge` still run a real bridge process against a swap-able upstream, in both stateless and stateful configuration (`:29-53`, `:52-153`), and `startUpstreamRestartBridge` takes the peer URL, so a header-capable handler can be supplied without editing the existing harness; a wrapper that reads `request.Header` and the body before delegating observes headers independently of the peer's session mode because the capture is at the HTTP layer. The existing restart tests use a body-only tool (`:155-218`), so they cannot regress from this change. The bridge fixture writes `catalog.refresh_interval: 5m` (`cmd/mcp-bridge/serve_test.go:131-160`, `writeBridgeConfig`), which bounds any test window shorter than five minutes to exactly one discovery pass.

### [AUTO-DECISION] entries (for coordinator persistence)

- **AD1 — mechanism: warm the execution session's tool cache with a targeted `tools/list`.** Why: it is the only seam that leaves emission to the SDK's own SEP-2243 implementation, so byte-level encoding, absent/null handling, integer range rules and header/body agreement cannot drift from the peer's validator; the SDK already sets `Mcp-Protocol-Version`, `Mcp-Method` and `Mcp-Name` on the same request. Result: in stateless mode at most one extra upstream `tools/list` page per header-bound call — page 0 only, with further pages requested only while the definition has not appeared and the cursor advances, so a definition that first appears on page `k` costs at most `k+1` list RPCs, all inside the single call-timeout context; zero extra list RPCs for body-only tools, and in stateful mode zero additional list RPCs while the cached page is still valid (a real page fetch after TTL expiry, which re-caches).
- **AD2 — bound the cost with a discovery-maintained header-annotation index.** Why: without it every stateless call would pay the extra RPC. Result: an in-memory per-runtime set of raw tool names that carry at least one `x-mcp-header`, replaced only after a fully successful discovery; a miss means "not header-bound" and keeps today's path.
- **AD3 — additive reason token `parameter_header_unsupported`.** Why: ticket 03 requires a specific, actionable code distinct from `tool_reported_error`/`upstream_protocol_error`; reusing `unsupported_capability` would conflate the protocol boundary with upstream interaction requests in both the client payload and the log, and its remediation text would be wrong. Result: one new value in each of three closed places (runtime reason vocabulary, the runtime error-info map, the dispatch message), classified `configuration`/non-retryable with the existing configuration remediation string; no event or field name changes; the logging contract row is extended.
- **AD4 — legacy rejection is per-call, after session acquisition and before any `tools/list` or tool execution.** Why: discovery-time rejection would remove working non-header tools from the same server (MB-001 shows query-only tools succeed), violating availability; a first-call-only check would be stateful and non-deterministic. Result: a stateless legacy header call still pays one connect/initialize, then returns `parameter_header_unsupported` with `not_started`.
- **AD5 — arguments are retained and headers are additive.** Why: the SDK peer rejects a header when the body parameter is absent and rejects a mismatch when it is present; stripping would break every compliant peer. Result: `arguments` bytes are unchanged; no bridge-side filtering.
- **AD6 — the annotation index is presence-based (any non-empty string `x-mcp-header` at any nesting depth, regardless of declared type).** Why: over-inclusion costs at most one wasted `tools/list` in a malformed-schema case, while under-inclusion would reproduce the defect; the SDK performs its own validation. Result: the scan is a simple JSON `properties` walk; no duplicate validation logic.
- **AD7 — a tool missing from the execution session's fresh list is not converted into a synthetic failure.** Why: a tool absent from the upstream's current list cannot produce a header/body mismatch, so the upstream's own answer is the truthful outcome and inventing a code would misdescribe a catalog-divergence case. Result: the warm scan completes, returns nil, and the single execution proceeds; no new code.
- **AD8 — admission ordering via a prepared-call seam in `ServerClient`.** Why: running the warm before admission would spend an RPC on every call rejected by an open breaker or a saturated slot, and would sit outside the per-call timeout; running it inside the admitted, timeout-bounded scope preserves both invariants with a small behavior-preserving refactor. Result: `CallTool` delegates to a new `CallToolPrepared` with a nil prepare, so existing callers and tests are unchanged.

## 4. DESIGN
<!-- specdd:design:start -->

**Approach.** Keep the bridge dumb about header encoding and make the SDK's own emitter reachable on the execution session. Three small pieces: (1) a discovery-maintained annotation index that decides *whether* a tool needs the extra definition fetch; (2) a warm routine that pages the executing session's `tools/list` until the tool definition is cached; (3) a legacy gate that fails before any warm or execution. A minimal `ServerClient` refactor runs the warm after admission and inside the call timeout.

**Components and contracts (`internal/upstream/dedicated.go`).**

1. `Dedicated` gains `headerTools map[string]struct{}` guarded by the existing `d.mu`. `Discover` builds the map while it iterates each page (the canonical schema bytes are already in hand in that loop) and swaps it in only after every page succeeded, immediately before returning the definitions. Any failure return leaves the previous map untouched (all-or-nothing, matching the existing catalog rule). Readers take the map under `d.mu`, following the file's existing read pattern.
2. A new unexported helper reports whether a tool's canonical `InputSchema` carries any non-empty string `x-mcp-header` value on any property at any depth under `properties` (AD6). It never validates header names or types; the SDK and the peer do.
3. A new unexported helper takes the executing session and a raw tool name, calls `session.ListTools` with an explicit non-nil params object starting at cursor `""`, follows `NextCursor` while the current page does not contain the name and the cursor advances, and returns an error only when a `ListTools` call fails. It returns nil when the scan completes without the name (AD7) and nil when the cursor fails to advance (the loop terminates; the SDK's own lookup then misses and the call proceeds un-warmed).
4. `CallTool` keeps its existing structure. After the session is acquired and the arguments are decoded, it selects a prepare function: if the index marks the tool header-bound, the prepare function checks the executing session's `InitializeResult().ProtocolVersion`; a missing result or a version `< "2026-07-28"` returns a `*CallError` with code `parameter_header_unsupported` and execution state `not_started`; otherwise it runs the warm helper. A body-only tool passes a nil prepare. The single execution call becomes `d.client.CallToolPrepared(ctx, session, params, prepare)`; result shaping and `failureOutcome` mapping are unchanged. Plain warm errors flow through `failureOutcome`, so they map to the existing safe codes.

**Component and contract (`internal/upstream/runtime.go`).** Add `CallToolPrepared(parent context.Context, session *mcp.ClientSession, params *mcp.CallToolParams, prepare func(context.Context) error) (*mcp.CallToolResult, error)` with exactly the current `CallTool` body plus, after a successful `AdmitCall` and before `session.CallTool`, a non-nil `prepare(ctx)` whose error is returned immediately. `CallTool` becomes a one-line delegation with a nil prepare. The prepare error path MUST NOT call `RecordFailure`/`RecordSuccess` (a definition read is not an execution outcome) and MUST NOT execute the tool. Everything else — nil session, timeout context, admission code mapping, JSON-RPC classification, `NeedsInput`, success accounting — is byte-for-byte unchanged.

**Component and contract (vocabulary).** Add the token `parameter_header_unsupported` to the reason vocabulary (`internal/observe/log.go:158-167`) and a runtime-error-info case (`internal/observe/envelope.go:103-133`) whose `ErrorInfo` is `{Code, Kind: configuration, Retryable: false, Remediation: "correct the server configuration or credentials"}` — identical to the existing configuration class, so the closed mapping stays one-to-one. Add a dispatch-message case (`internal/service/tools.go:1051-1064`) with a fixed payload-free message. The evidence-class mapping keeps its default (`unavailable`); the distinguishing signal is the error code, not a new evidence class.

**Invariants.** (I1) No bridge code writes a `Mcp-Param-*` header or alters `arguments`; emission is the SDK's (R2/R4). (I2) The index has no false negatives for tools in the published catalog: it is updated inside the same successful discovery that later produces the published definitions, before publication, and only a *later* successful discovery can remove an entry — and a tool removed upstream cannot succeed regardless (AD2, AD6). The reverse skew (index ahead of publication) costs at most one warm request. (I3) A body-only tool executes with a nil prepare: not one additional upstream RPC (R3). (I4) The legacy gate runs before any `tools/list` and before `session.CallTool`, so a legacy header call performs exactly one initialize and zero tool executions (R6/AD4). (I5) The warm runs after admission and inside the call-timeout context, so a rejected call spends nothing extra and the whole header-tool operation is bounded by one configured call timeout (AD8). (I6) Prepare failures never touch breaker counters and never execute the tool (AD8). (I7) No session is retained in stateless mode; the warm uses the same ephemeral session as the execution and it is closed by the existing deferred close (R1/R11). (I8) A failed discovery leaves the previous index intact, so a refresh failure cannot silently downgrade a header tool to the old path.

**Value selection and encoding (decision 2).** The bridge never decides per-parameter. At call time the SDK walks the session-fetched definition, matches annotated property paths against `arguments`, skips absent and `null` values, and encodes strings as-is (Base64 when not header-safe ASCII), booleans as `true`/`false`, and integers as base-10 text when they are integral and within the JavaScript safe-integer range; anything else yields no header. Because the peer requires header/body agreement, a value the SDK cannot encode surfaces as the peer's own rejection, reported through the existing `upstream_protocol_error`/`tool_reported_error` classes — the bridge adds no pre-flight duplicate of those rules and the published schema already rejects wrong-typed arguments at admission.

**Sequences.** Stateless header call: catalog admission → `CallTool` → closed check → connect (initialize) → index hit → version `>= 2026-07-28` → `CallToolPrepared` admits → warm `tools/list` (page 0, and further pages only if the name is absent and the cursor advances) → one `tools/call` whose transport emits `Mcp-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, `Mcp-Param-*` → result shaped unchanged → session closed. Stateless body-only call: identical minus index hit, warm, and prepare. Stateful header call: `sessionFor` → index hit → version check → warm (cache hits while the entries are valid; a real page fetch when the TTL expired or was zero, which re-caches) → execution on the same cached session. Legacy header call: session acquired → index hit → version `< 2026-07-28` → `parameter_header_unsupported`, `not_started`, zero `tools/list`, zero execution.

**Alternatives rejected.** *(a) Bridge-side `RoundTripper` emitter writing `Mcp-Param-*` from the catalog schema:* duplicates SEP-2243 base64/primitive encoding, needs schema and version plumbing into the transport, and can silently diverge from the SDK's own emission when a stateful session already has a warm cache — rejected on correctness and maintenance cost. *(c) Force `stateless: false` for affected servers:* changes a documented default, pins sessions, and forfeits the restart-resilience property that `TestUpstreamRestartSurvivesInDefaultStatelessMode` exists to protect — rejected. *(d) Extend `core.Upstream` to carry the published definition:* removes only the index (not the extra RPC), and widens a public interface plus every fake and service call site — disproportionate for a boolean derived from the same upstream. *(e) Discovery-time rejection of legacy header tools:* drops working non-header tools — rejected (AD4). *(f) A bridge-local pre-flight that computes and attaches headers itself:* same duplication as (a) — rejected.

## 9. CRITIC HANDOFF

**Highest-risk assumptions and decisions.** (1) The chosen mechanism depends on the SDK's client-side cache being the only definition source; verify that no supported public API could have seeded it more cheaply. (2) The index (AD2/AD6, I2) must be shown free of false negatives for published tools across a refresh failure and a concurrent refresh/call. (3) The `CallToolPrepared` refactor must be byte-for-byte behavior-preserving for a nil prepare, including breaker accounting and timeout scope. (4) The additive token must be registered in all three closed places consistently, with the configuration remediation string exactly equal to the existing class (AD3). (5) AD7 (a vanished tool proceeds un-warmed) is a deliberate boundary behavior, not an oversight. (6) The modern test peer must stay stateless at the transport layer; any stateful construction re-introduces the H1 failure mode where the version pin is filtered away and the oracle silently measures the legacy gate.

**W09E candidate-bound matrix.**
- *Lifecycle:* producers/consumers/clear paths of the annotation index (built only in a successful `Discover`, swapped once, never cleared except by a later successful discovery); bootstrap (startup discovery populates it before the catalog publishes), ordinary operation, refresh failure (index retained), restart (rebuilt). Counterexample considered: two overlapping refreshes where the older completes last — publication is the existing last-completion-wins pointer swap, so the catalog keeps the older discovery and the index keeps the matching entry; catalog and index therefore describe the same tool set, and a call in that window can at worst spend one warm request.
- *Shared state:* writers of the index are `Discover` only, under the runtime mutex; the session cache is written by the SDK on the same goroutine path as the call. Walked schedule: call A warms page 0 while a refresh replaces the index — A already chose its prepare; correctness of emission depends only on the session's own cache, not on the index. Breaker writers are untouched; the prepare path writes nothing.
- *Contract:* R1–R11 all map to AC ids (Coverage line); T1–T4 cover them; ticket criteria are 1:1 with AC ids; boundary cases covered are legacy, absent/null arguments, non-primitive values, invalid/absent annotations, a vanished tool, a paginated peer, cache TTL zero, refresh failure, a control tool on a legacy peer, and a rejected-by-admission call.

- *Observability:* traced emission → sink for the new token (AC03-2), no metric/label/event/field addition, and the three justified exceptions with reasons and consequences.
- *Repair closure:* any amendment must repair the root invariant (the SDK is the only emitter; the index decides only whether to warm; admission precedes the warm; the modern peer must be stateless to negotiate) across the clauses, invariants and fixtures rather than one sentence.
