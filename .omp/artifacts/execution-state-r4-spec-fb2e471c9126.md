# Header Parameter Transit — Header-Annotated Tool Parameters Through the Bridge (SpecDD, feature `header-parameter-transit`)

## 1. STATUS

Spec ID `header-parameter-transit`, revision r4. State: **DRAFT** (full re-plan from primary sources; ready for staged independent review; no execution authorization). Objective: a `tools/call` for a tool whose published input schema annotates parameters with `x-mcp-header` must reach a modern upstream through the bridge's normal call path in the default `stateless: true` configuration, without pinning a session and without weakening restart resilience, while the explicit-stateful path and the legacy-protocol boundary are deterministic and named. Evidence scope: backlog MB-001, tickets `issues/01`–`issues/04`, the working tree and go-sdk v1.8.0 sources cited in §3.

**Revision history.** r1 (initial). r2 (CR1 REQUEST CHANGES). r3 (revised text). **r4 is a full re-plan, not a repair:** every mechanism, cost statement, oracle and command below was re-derived from the tree and the SDK; prior review rounds (r1/r2/r3) are treated as evidence of prior failure, not as a baseline to preserve. The r4 deltas that matter: (i) the definition pass paginates until the tool appears, and its worst case is *every page of the upstream's tool list*, not page 0 (r3's AD1 claimed page 0 only while its design paginated — the contradiction is removed, and the cost is stated as a paginated worst case inside the single call-timeout); (ii) any failure of that pass is `not_started`, performs zero executions and performs zero breaker accounting; (iii) a stateful cache hit exists only when the upstream advertises a positive list TTL, because the SDK deletes zero-TTL entries on read while its tool lookup ignores TTL, so a stateful header call re-fetches one or more definition pages per call on a zero-TTL peer; (iv) the explicit-stateful probe is a *control* that must pass on the pre-change build, not a RED case; (v) the legacy peer is constructed and asserted through the verified older-only fallback chain; (vi) the vocabulary assertion lives inside the enveloped upstream test file, so no envelope write path is added; (vii) every validation command is an anchored alternation that matches every oracle it is said to cover, and the one pre-existing regression test the plan references is baseline-verified before it may gate anything. Section ids and structures are unchanged; §10 ENVELOPE is the state writer's binding surface.

## 2. REQUIREMENTS
<!-- specdd:requirements:start -->
**R1 (default stateless transit).** With default configuration (`stateless` unset ⇒ true, `internal/config/config.go:48-52`), a `tools/call` for a tool whose last successful discovery published an input schema containing an `x-mcp-header` annotation must reach the upstream as exactly one execution whose outbound HTTP request carries the parameter values both in the JSON `arguments` object and in matching `Mcp-Param-<header-name>` request headers. No upstream session may be retained between calls to achieve this.

**R2 (single emitter, bridge ensures the definition).** The bridge must not construct, encode, re-encode or strip `Mcp-Param-*` headers. Emission must be the go-sdk client's, driven by the tool definition present in the executing session's `tools/list` cache. The bridge's only responsibility is to ensure that definition exists on the execution session for tools it knows to be header-bound; per-parameter selection and value encoding are the SDK's SEP-2243 rules. The bridge's knowledge must be derived from the same published schema the catalog serves and must never disagree with it in the under-inclusive direction for an already-published tool.

**R3 (control preservation).** A tool with no `x-mcp-header` annotation must behave exactly as today: no additional upstream RPC, no additional header, identical arguments bytes and identical result content.

**R4 (argument retention).** Header-bound values must remain in the JSON `arguments` object, byte-preserved through the existing decode/encode path; the headers are additive. Removing a value from `arguments` is prohibited because the SDK peer rejects a header whose body parameter is absent and rejects a mismatch when it is present.

**R5 (explicit stateful mode).** With `stateless: false`, a header-bound tool must succeed using definitions present on the runtime's single cached session; no extra session, no second execution. When the peer's advertised list TTL is positive and unexpired, the call must perform no definition RPC; when it is zero (or expired), the call may perform the definition pass before its single execution.

**R6 (legacy boundary).** When the executing session negotiated a protocol version lower than `2026-07-28` and the tool is header-bound, the bridge must answer with the named, payload-free failure code `parameter_header_unsupported` and execution state `not_started`, with zero upstream tool executions, zero `tools/list` warm request, and no breaker mutation. It must not answer with `tool_reported_error` or `upstream_protocol_error`, and it must not reject discovery (which would remove working non-header tools on the same server).

**R7 (documented boundary).** Repository documentation must state which protocol versions carry parameter headers, how the bridge behaves in stateless and stateful mode, the exact failure code for older upstreams, the operator action, and the cost of the definition pass.

**R8 (payload-free failure vocabulary).** Every failure path on the header call path must be payload-free (no tool names, argument values, header values, URLs or tokens in messages) and must use the existing safe code set, except for the single additive reason token in R6, which must be registered consistently in the closed runtime reason vocabulary, the client-facing dispatch code and the logging contract. No new log event name, field name, metric family or metric label is permitted.

**R9 (deterministic reproduction).** A test that drives the bridge's own Tool server against a controllable peer must reproduce the defect and record the negotiated protocol version, the presence or absence and value of each parameter header, and the outbound arguments body, in both default stateless and explicit stateful mode, with no dependency on the live github upstream.

**R10 (deployed verification).** The shipped build must be verified on the live deployment against the github upstream: the header-bound call returns content, the query-only control succeeds in the same window, and structured logs for the header call show no `tool_reported_error` and no `upstream_protocol_error`. This requirement is operator-gated and outside the code envelope.

**R11 (restart resilience).** The restart contract must be preserved: a stateless header call opens a fresh session, survives an upstream generation swap, and succeeds against the new generation on a subsequent call.

**Non-goals.** No configuration key, default change or `stateless` policy change; no session pinning, eviction or reconnect policy; no go-sdk upgrade or vendored patch (stays v1.8.0, `go.mod:11`); no change to `core.Bridge.Dispatch`, catalog publication, search/embedding, the breaker state machine, metrics, capacity or readiness; no new log event/field, metric family or label; no retry/replay of an upstream call; no bridge-side transport-header emitter, build tag or protocol-patch hack; no change to the upstream server's own protocol implementation.

### [AUTO-DECISION] entries (for coordinator persistence)

- **AD1 — mechanism: warm the execution session's tool cache with a paged `tools/list`, paginating until the tool appears.** Why: it is the only seam that leaves emission to the SDK's own SEP-2243 implementation, so byte-level encoding, absent/null handling, integer rules and header/body agreement cannot drift from the peer's validator; the SDK already sets the standard headers on the same request. Result: in stateless mode the call performs at most one definition pass; the worst case is the number of pages up to and including the page holding the tool (and no more than the upstream's whole list when the tool has vanished), each page a separate RPC, all inside the single call-timeout context, with duplicates suppressed by paging forward from cursor `""`.
- **AD2 — bound the cost with a discovery-maintained header-annotation index.** Why: without it every stateless call would pay the definition pass. Result: an in-memory per-runtime set of raw tool names carrying at least one valid `x-mcp-header`, replaced only after a fully successful discovery; a miss keeps today's path. A stale miss can only occur after the upstream changed its schema inside one refresh interval, and then the peer answers with a safe payload-free rejection (no execution of the tool's documented effect).
- **AD3 — additive reason token `parameter_header_unsupported`.** Why: ticket 03 requires a specific, actionable code distinct from `tool_reported_error`/`upstream_protocol_error`; `unsupported_capability` would conflate a protocol boundary with upstream interaction semantics. Result: one new value in each of three closed places (runtime reason vocabulary, the runtime error-info map, the dispatch message), classified `configuration`/non-retryable with the existing configuration remediation string; no event or field name changes.
- **AD4 — the legacy rejection is per call, after session acquisition and before any `tools/list` or execution.** Why: discovery-time rejection would remove working non-header tools from the same server; a first-call-only check would be stateful and non-deterministic. Result: a stateless legacy header call pays one connect/initialize and then returns `parameter_header_unsupported` with `not_started`.
- **AD5 — arguments are retained and headers are additive.** Why: the peer rejects a header when the body parameter is absent and rejects a mismatch when present; stripping would break every compliant peer. Result: arguments bytes are unchanged; the bridge performs no filtering.
- **AD6 — the index is presence-based** (any non-empty string `x-mcp-header` under a `properties` object at any nesting depth, regardless of the declared type). Why: over-inclusion costs at most one wasted definition pass, while under-inclusion reproduces the defect; the SDK performs its own validation and already excludes tools with invalid annotations from the list. Result: a simple JSON walk, no duplicated validation logic.
- **AD7 — a tool absent from the session's fresh pages is not converted into a synthetic failure.** Why: a tool absent from the upstream's current list cannot produce a header/body mismatch, so the upstream's own answer is the truthful outcome. Result: the pass completes without the name, returns nil, and the single execution proceeds; no new code.
- **AD8 — admission ordering via a prepared-call seam in `ServerClient`.** Why: running the pass before admission would spend an RPC on every call rejected by an open breaker or a saturated slot, and would sit outside the per-call timeout; running it after admission keeps both invariants with a behavior-preserving refactor. Result: `CallTool` delegates to a prepared variant with a nil prepare function, so existing callers are unchanged; a prepare failure returns before any execution and before any breaker accounting.
- **AD9 — the vocabulary assertion lives in the enveloped upstream test file.** Why: the classification is part of the failure contract the upstream call path emits, and asserting it from `internal/upstream/header_params_test.go` (which may import `internal/observe`) needs no envelope widening. Result: no write path is added; the coordinator is informed that this placement is deliberate.

## 4. DESIGN
<!-- specdd:design:start -->

**Approach.** Keep the bridge ignorant of header encoding and make the SDK's emitter reachable on the execution session. Three small pieces: (1) a discovery-maintained annotation index that decides *whether* a tool needs the definition pass; (2) a paged definition pass that populates the executing session's cache; (3) a per-call legacy gate that fails before any pass or execution. A minimal `ServerClient` seam runs the pass after admission and inside the call timeout.

**Header-bound detection (`internal/upstream/dedicated.go`).** A new unexported helper takes a canonical input schema (`internal/core/core.go:248`) and reports whether any JSON object under a `properties` key at any nesting depth contains an `x-mcp-header` member whose value is a non-empty JSON string. It does not validate header names, types, required-ness or `additionalProperties`. This is sound because the SDK client's `filterValidTools` runs before the page is cached and before the bridge's discovery sees the tools, so a tool with an invalid annotation never enters the bridge catalog; the index therefore cannot under-approximate a published header-bound tool. The index is a `map[string]struct{}` of raw tool names on `Dedicated`, guarded by the existing mutex, rebuilt on every successful discovery and swapped in only after every page succeeds, before the definitions are returned to the caller; a failing discovery leaves the previous index intact, matching the existing catalog rule. Readers take the map under the mutex.

**Definition pass.** A new unexported helper takes the session and a raw name and calls `session.ListTools` with an explicit non-nil params object starting at cursor `""`; while the current page lacks the name and `NextCursor` differs from the previous cursor, it continues from that cursor. It returns nil when the name is found, nil when the list is exhausted or the cursor stops advancing, and the error when a `ListTools` call fails. Forward paging is required because the SDK's lookup scans every cached page, so stopping at page 0 would miss a tool the upstream places later; the worst case is the whole list, which is the correctness cost AD2 accepts.

**Call path (`internal/upstream/dedicated.go`, `internal/upstream/runtime.go`).** After the session is acquired and the arguments are decoded, `Dedicated.CallTool` selects a prepare function: for a body-only tool it is nil; for an indexed header-bound tool it first compares the session's `InitializeResult().ProtocolVersion` with `2026-07-28` (or treats a missing result as below) and returns the typed call error `parameter_header_unsupported` with `not_started` when the comparison fails, and only otherwise runs the definition pass. The call becomes the prepared variant of `ServerClient.CallTool`: the existing body, unchanged, plus a non-nil prepare invoked after a successful admission and before the session call, whose error is returned immediately. The prepare error path must not call failure or success accounting (a definitions read is not an execution outcome) and must not execute the tool; the deferred admission release still runs. Existing callers delegate with a nil prepare, so their behavior is byte-identical.

**Why the gate is per call and reads the session's version.** The version is established by the handshake of *this* session, which is the authority for this request; a discovery snapshot is a different session (stateless mode) and could be stale. The check runs before the definition pass so a legacy remote pays no extra RPC, and before execution so no tool effect is attempted under a protocol that cannot carry the parameters. The `upstream_ephemeral_handshake` record remains the observability signal for the negotiated version and is not used as the gate's input.

**Cost, stated exactly.** Stateless header call: one connect, one definition pass covering pages until the tool appears (worst case: every page of the list), one `tools/call`, one close. Stateful header call: no connect; the definition pass pages while the cache lacks the entry; on a positive-TTL peer the cache hit costs zero definition RPCs (and a `tools/list` on a modern session returns the cached page without a request), while on a zero-TTL peer the SDK deletes the entry on the first lookup, so each header call performs at least one definitions RPC and then one `tools/call`. All RPCs of one call share the call-timeout deadline (`internal/upstream/runtime.go:178`, `internal/upstream/runtime.go:184`); the plan adds no per-RPC timeout and no page cap, because a cap would risk the very false negative this feature exists to fix. Standard headers (`Mcp-Protocol-Version`, `Mcp-Method`, `Mcp-Name`) and parameter headers are claimed only for sessions negotiated at `2026-07-28` or later; below that, the transport emits none.

**Failure behavior.** Gate failure: `parameter_header_unsupported`, `not_started`, zero executions, zero breaker accounting. Definition-pass failure: the existing `failureOutcome` mapping applies, so the code is one of the existing safe codes (`backend_unavailable`, `upstream_protocol_error`, `deadline_exceeded`, …) with `not_started` and zero executions; no new code is introduced for it. Execution: unchanged, including `tool_reported_error` for tool-level errors. Messages stay fixed and payload-free; the new code has a fixed message.

**Sequences.** Stateless body-only: admission → connect → one `tools/call` → close. Stateless header-bound: admission → connect → index hit → version gate → definition pass (pages until found) → one `tools/call` with arguments and parameters → close. Stateful header-bound: cached session → index hit → gate → pass (cache hit or refetch per TTL) → one `tools/call`. Legacy header-bound: session → index hit → gate fails → `parameter_header_unsupported`/`not_started`, no list, no call.

**Alternatives rejected.** *(a)* A bridge-side `RoundTripper` emitter: duplicates SEP-2243 encoding and the version gate, can disagree with the SDK's own emission when a stateful cache is already warm, and needs schema/version plumbing into the transport — rejected on correctness and maintenance. *(c)* Forcing `stateless: false` for affected servers: changes a documented default, pins sessions, and forfeits restart resilience — rejected. *(d)* Extending `core.Upstream` to carry the published definition: removes only the index, not the definition pass, and widens a public interface plus every fake — rejected. *(e)* Warm during discovery in stateless mode: the discovery session is closed, so the cache would be discarded — rejected as vacuous.

**Invariants.** (I1) No bridge code writes a parameter header or alters arguments; emission is the SDK's. (I2) The index is updated by, and only by, a fully successful discovery, before publication, so a published header-bound tool is never missing from the index at publication time; a later successful discovery may remove the entry, and a tool the upstream removed cannot succeed anyway. The only skew is a schema change inside one refresh interval, which yields a safe payload-free rejection. (I3) A body-only call has no prepare: zero extra RPCs. (I4) A legacy header call performs zero lists and zero executions. (I5) A prepare failure yields `not_started` and no breaker accounting.

## 8. RELEASE AND RECOVERY

**Order.** Merge to the main branch after review → build and push the image (operator/registry-owned; this pipeline must not write `registry.localdomain:5000`) → deploy through the operator's Portainer flow → wait for readiness → record the image reference, the container identity and the catalog revision → run T4.

**Rollback.** Redeploy the previous image digest. There is no schema, state or data migration; no session is pinned and no configuration changed, so rollback is a plain image swap, after which header calls return to the pre-change behavior (a payload-free upstream rejection in the same scenario). The catalog is republished by discovery on the next refresh.

**Irreversible steps.** None.

**What operators must know.** (1) `2026-07-28` and later carry parameter headers; below that the bridge now answers a header-bound call with `parameter_header_unsupported`/`not_started` instead of letting the SDK silently omit the headers — this is intentional fail-closed behavior, and ticket 04's upstream must negotiate the newer version or be upgraded/repointed. (2) A header-bound call pays one definition pass (up to every page of the upstream's tool list) inside the single `limits.call_timeout`; on a zero-TTL peer the same is true in stateful mode, so raise the call timeout for large catalogs. (3) A body-only tool pays nothing and keeps its behavior. (4) The failure is logged with the existing fields and appears in Loki as `error.code=parameter_header_unsupported`.

## 9. CRITIC HANDOFF

**Highest-risk assumptions and decisions.** (a) The definition inserted by the pass on the execution session is visible to the immediately following call — test-verified by AC02-1 rather than assumed at runtime; if it fails, T2 reports BLOCKED. (b) The index cannot under-approximate a published header-bound tool because successful discovery writes it before publication; the only skew is a schema change within one refresh interval, which is a safe, payload-free rejection (a documented limitation, not hidden). (c) On a zero-TTL peer a concurrent stateful header call can lose the cache entry between the pass and the call and fail safely with an existing code; this is a `dependency`-class availability limitation, never a data-corruption or execution-replay risk. (d) The legacy gate is per call and reads the executing session's version; a discovery snapshot is deliberately not used.

**Coverage gaps the reviewer should probe.** (i) The pagination oracle pins exact counts for a `PageSize: 1`, three-tool fixture; confirm the fixture's registration order yields the target last and that the counts are taken after discovery. (ii) AC01-4 is a control and must not be counted as RED evidence; confirm the receipt separates controls from failures. (iii) AC02-3 depends on a pre-existing test; confirm T1's baseline is recorded and that a red baseline yields a blocker, not an attributed failure. (iv) The vocabulary test lives in the upstream package by design (AD9); confirm that placement does not hide a drift between the dispatch message and the runtime map.

**W09E risk matrix (evidence + counterexample).**
- *Lifecycle*: stateless execution sessions are per call; the pass must run on that session (`internal/upstream/dedicated.go:359`). Counterexample rejected: warming a discovery session caches nothing after it closes. Evidence: the discovery close path at `internal/upstream/dedicated.go:71`.
- *Shared state*: the index is per runtime, read by concurrent calls and written by refreshes; the all-or-nothing swap plus mutex access mirrors the catalog rule. Counterexample: rebuilding it per call would add RPCs and could disagree with the published catalog.
- *Contract*: `x-mcp-header` presence is the only signal; invalid annotations are invisible because the SDK's filter runs before caching. Counterexample: an annotation value that is a number is dropped by the SDK, so the bridge cannot publish or call that tool — an existing SDK behavior, not this fix's regression.
- *Authority*: planner authors this specification; the engineer implements T1–T3; T4 is operator-gated; the live deployment is not executable from the pipeline.
- *Observability*: one reason value in three closed places; no unbounded label; the failure is queryable by `error.code` and the request outcome. Counterexample rejected: a metric label carrying per-code values.
- *Repair closure*: closure requires the recorded pre-change failure and the post-change pass for the same assertion, plus the delivery-gate receipt; a claim of “passes after” without the RED run is not closure.
