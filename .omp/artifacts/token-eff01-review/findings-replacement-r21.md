VERDICT: REQUEST CHANGES

Subject: specification, initial replacement pass, `r21-replacement` on-disk. The eight r19 findings are genuinely closed (no-marker eviction, AC4 non-derivation, literal prefixes, `remaining_*` literals, event ownership, T4 test roots, handle-logging ban, R4 scoping). The six carried invariants are present in outline, but two are not yet testable as stated.

**1. [HIGH] §2 R11(g), §4 AC23 — the pinned-width list is incomplete, so envelope feasibility can pass an over-ceiling config.**
R11(g) and AC23 pin only `total_bytes`/`remaining_bytes` (20 digits), `total_pages`/`remaining_pages` (10), `handle` (43), and `upstream_code` (`max_upstream_code_bytes`, serialized). They omit `page` (up to 10 digits at the uint32 cap), and the terminal's `retention` value (longest code `result_aggregate_capacity_exceeded`, 34 chars; shortest 23), plus `execution_state`/`paging_required`/`is_error`. R11(g) says the computation "uses exactly these pinned widths — never smaller observed values," and AC23 says the envelope is "built at R11(g)'s pinned widths (…)" — an exhaustive-sounding list. A checker built from AC23 using `page: 1` and a 24-char retention string undercounts by up to 9–11 bytes, more than the required 6-byte headroom. Consequence: a load-accepted config can emit a page or terminal whose serialized envelope exceeds `delivery_ceiling_bytes`/`preview_ceiling_bytes`, violating R5/R10 and the per-terminal bound invariant. Fix: pin every variable-width metadata field at its maximum (`page` at 10 digits, `retention` at the longest terminal code, literals for the fixed fields), and give AC23 one subtest per envelope (preview/page/terminal) so a loader validating only one relation fails.

**2. [MEDIUM] §2 R6/R7/R16, §4 AC8/AC39/AC43 — the 256-byte charge's disposition on marker-cap eviction and retirement is unspecified.**
R6 says the reservation converts into the marker's charge "and leaving when the marker clears"; AC39 says the charge replaces the reservation "until the marker clears at `tombstone_ttl`." R16 separately evicts markers beyond `max_markers_per_namespace`; that is an eviction, not a clearing, so the charge's release is undefined — either it leaks indefinitely (spurious `result_aggregate_capacity_exceeded`) or is released without a stated rule. AC39 asserts marker count and handle code, not aggregate bytes. Likewise, R7's retirement commit evicts entries; R16 makes eviction install markers, but the spec never says whether retirement-evicted entries install markers, release reservations, or what happens to the namespace's already-live markers. AC8 asserts only the tombstone's 256-byte release. Consequence: aggregate accounting across the marker cap and retirement is implementation-defined, and the carried "retired-marker lifetime and accounting" invariant is not testable. Fix: state that cap eviction releases the charge immediately (or that it remains until a named sweep) and that retirement clears/release-accounts every namespace record; assert exact aggregate deltas in AC39 and AC43.

**3. [MEDIUM] §2 R12, §7 Events, §4 AC13 — the "registry equals the emitted set" claim has no oracle, and §7's event closure has no AC.**
R12 says the registry's equality with the emitted set "is asserted by AC13's runtime oracle, never assumed." AC13(a) actually asserts equality with a frozen 31-value literal; AC13(b) injects one unlisted operation; AC13(c) covers only `search_tools` and `retrieve_result` producers. Nothing exercises the eleven pre-existing non-vocabulary literals, so if that hand-built list omits one, the new enforcement drops a legitimate record and every AC still passes. Separately, §7 says `eventMessage` is closed and that T2 "asserts this in `TestLogLabelEnumeration`," but AC13 defines no unregistered-event-name case or expected violation-record shape. Consequence: the finite-label invariant is only half-oracled. Fix: add an unregistered-event-name case to `TestLogLabelEnumeration` (expected record, no injected value, counter increment), and either add producer checks for the eleven values or restate the claim as "equals this frozen list."

**4. [LOW] §2 R6, §6 `max_bytes_per_namespace`, §4 AC7 — reservation accounting and the namespace-infeasibility outcome are unstated.**
R6 defines the 256-byte reservation only in the *aggregate* footprint. It does not say whether that reservation counts against the per-namespace byte bound. Relation (c) permits `max_bytes_per_namespace == max_retained_result_bytes`; if the reservation counts there, an entry at its per-entry cap cannot be admitted, and no terminal code covers a namespace-bound refusal (`result_capacity_exceeded` is defined only for the per-entry cap). Fix: state the per-namespace accounting domain and either define the refusal terminal or add a relation proving the case unreachable; extend AC7.

**5. [LOW] §2 R11(g), §5 T1, §4 AC23 — the feasibility widths are restated three times.**
R11(g), T1, and AC23 each enumerate the pinned widths, and the restatements are how finding 1 slipped through. Make R11(g) the sole normative list and have T1/AC23 reference it.
