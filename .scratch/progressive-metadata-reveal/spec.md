## 4. DESIGN

All new mechanisms below are **[INFERENCE] selected design**, not existing implementation or SDK guarantees.

### 4.1 Shared server, authoritative session projections
Retain the single shared MCP server/streamable transport, existing initialize capabilities, three built-ins, prompts/resources and upstream execution infrastructure. Do not create per-session SDK servers or change the server factory.

Introduce one bridge-owned projection coordinator. An exposure owner is keyed by the trusted SDK session ID plus a unique process-local owner epoch, never by bearer alone. Associate it with the existing authenticated inbound admission incarnation. Each live owner holds logical discovery interests and one immutable projection containing:
- owner epoch and monotonic projection generation;
- the accepted runtime/configuration generation from which it was derived;
- a deterministically name-sorted complete descriptor sequence;
- an immutable exposed-name→logical-target/binding/schema map.
Two sessions sharing a bearer have distinct owners. Exposure and cursor state are transient and do not advance catalog_revision. Own mutable metadata once at preparation boundaries; published containers/descriptors are immutable. Do not deep-copy the whole projection for every list request or keep upstream clients alive merely for exposure.

Receiving middleware handles `tools/list` completely from the requesting owner's projection, rather than filtering a page already produced by SDK enumeration. It gates all direct pin/dynamic `tools/call` admissions using that same projection. The three built-ins retain their existing handlers; search/describe receive trusted owner context from middleware. Other MCP methods continue through the existing shared server unchanged. A list-only filter is insufficient and prohibited.

### 4.2 Union registry and SDK integration
Maintain a union registry of exposed direct names across current pins and live projections. Track references so one owner's cleanup never removes a name another owner or pin still needs. Union entries carry only the minimal descriptor/dispatch identity required by the SDK; handler closures do not capture session projections, historical bindings, source metadata or retired runtime assemblies.

The SDK shared registry is not the visibility or direct-dispatch authority. For every direct pin/dynamic `tools/call`, receiving middleware validates the trusted owner and exposed name against one immutable projection and, under the short admission barrier, captures one admissible accepted Assembly/generation, logical target, exact binding and its input schema, and ordinary execution lease belonging to that same Assembly. Binding/target/schema provenance must agree with the admitted projection and accepted generation; missing, stale or inconsistent inputs reject without upstream dispatch. Release all bridge/publication/registry locks before execution. Introduce a new request-scoped bound-execution adapter consuming that captured tuple, the authenticated request context and raw direct-call arguments. This adapter must be extracted/bound from the existing service execution behavior; the inspected handlers do not already provide this tuple-taking entry point (`internal/service/tools.go:211-259,663-709`). No exact Go symbol is established here.

The adapter validates/decodes raw arguments against the captured binding's schema, preserving existing direct-pinned validation, authentication, upstream-session reuse, result envelopes and error mapping. It must neither recapture Runtime.Current nor re-resolve a target/binding/schema from a mutable map, invoke an SDK union-handler closure, consult the latest SDK descriptor, or call the next SDK `tools/call` handler for an admitted direct call. Do not route direct arguments through the generic `call_tool` envelope or substitute its distinct validation/error mapping: direct-pinned `tools.go:239-248` and generic `:688-697` remain separate public contracts. The bound adapter is the sole owner of execution result/error mapping and, once ownership transfers to it, exactly-once lease release on success, validation failure, execution error, cancellation or panic unwinding. Before that transfer, admission owns release of any acquired lease on rejection. Middleware forwards the mapped result/error without remapping; transport serialization remains the SDK's responsibility. No request-scoped adapter is retained in the union registry.

Shared/latest SDK descriptors cannot validate against a different projection's schema. Union handlers remain defensively owner-gated for any path reaching them, with no unguarded fallback. Unknown, undiscovered, obsolete, retired or inadmissible names fail without upstream dispatch. The three built-ins, including generic `call_tool`, continue through their existing SDK handlers and preserve their existing contracts. Registry removal/replacement after admission therefore cannot turn an admitted direct call into an SDK “tool not found” failure; PR-AC6/7/9 require that observable race outcome, one captured tuple, direct-versus-generic contract preservation and exactly-once mapping/release.

Prebuild complete union descriptor changes. Because public AddTool may panic and returns no error, validate changed SDK registrations before projection commit using the same public AddTool validation in a non-serving, sessionless validation registry, converting only descriptor/schema validation failure into the existing finite candidate failure. This validation registry is not a client server, factory replacement or transport. Reuse prepared immutable descriptors and validate only changed registrations. Do not reinterpret a production AddTool call as an error-returning transactional API or swallow arbitrary panics as successful publication.

Publish immutable projections first, then apply prepared shared-registry removes/adds while publication writers remain serialized. Middleware readers/admission never depend on seeing intermediate SDK registry states. Complete registry reconciliation before releasing discovery success. Changed exposure in a second session may require re-registering the relevant union entry to obtain the existing standard list-change signal even when the descriptor bytes already exist in the union. Unchanged repeated discovery does not re-register, change generation or emit a synthetic signal. No second explicit notification mechanism is added.

Registry operations occur after semantic projection commit, so their asynchronously scheduled signals cannot precede the projection they announce. Broadcast/coalesced SDK signals may also reach sessions whose own descriptor set is unchanged; they contain no tool metadata and grant no visibility. Reference changes caused solely by retiring an owner must not trigger duplicate signals to unchanged live owners unnecessarily. Unexpected postcommit registry/response failures are failures after observable publication: keep committed state, use existing finite failure reporting and do not report discovery success before required reconciliation completes. Do not roll back state another request may have observed.

### 4.3 Identity, pins and interests
Logical target K is `(existing server identity, exact upstream raw tool name)`. Retain canonical pin names and opaque dynamic identities; titles never become identifiers.

For each owner: pinned K has only its canonical descriptor; unpinned discovered K has only its opaque descriptor; unpinned undiscovered K has neither. Successful search/describe of pinned K records interest without duplicating its descriptor. Unpinning creates a dynamic replacement only for owners with that interest. A departed target loses interest; reappearance does not resurrect it.

Recompute descriptor and binding together for dynamic→pin and pin→dynamic changes. Swap complete projection pointers, not individual descriptor/name entries. No duplicate, replacement gap, redirect or compatibility alias is exposed. Independent requests across a commit may see different complete projections. A page already captured from the old projection remains immutable and valid as that old response.

### 4.4 Effective metadata and presence
Reuse the existing metadata derivation/conversion pipeline; do not create a reveal-specific overlay convention:

`effective(K) = overlay(overlay(SDK-normalized source(K), explicit defaults(server(K))), exact patch(server(K), rawName(K)))`.

Missing layers contribute nothing. Recursively merge objects and replace scalars/arrays. Omission inherits; supported explicit false/empty values override. Removing members/layers recomputes from current source/configuration, never cached effective corrections.

Supported inventory remains description, title, icons, annotation title/four hints and supported nested `_meta`. Names/input/output schemas are protected. Persist source only. Describe preserves its existing envelope, separate `upstream_metadata`/effective view and `metadata_override_fields`. A winning default uses `layer:"server_default"`; a winning exact-tool patch uses `layer:"tool"`, whether the target is pinned or revealed and regardless of exposed name. These are the complete retained Layer values. Do not introduce `unpinned_tool` or identity-dependent provenance. Given identical accepted inputs, pin/reveal effective metadata and winning field-path/layer provenance agree, apart from their intentionally different exposed identities. No correction yields an empty provenance list.

Absent source annotations with no valid annotation-object patch remain absent. Description/title/icons/`_meta`-only corrections never invent annotations. A valid annotation-object patch may introduce effective presence while source remains absent; empty annotations do not assert safety. Retain SDK-representable destructive/open-world nil/false/true and scalar read-only/idempotent normalization without fabricated original-key provenance. Configured annotations:null, null hint members, invalid types and unsupported fields reject the whole candidate. Supported nested `_meta` null remains a value, not deletion.

Keep `tool_metadata.defaults/tools` shapes. Defaults may apply to any eligible same-server target when pinned or revealed. Exact entries match exact same-server raw names in the candidate catalog/pins, not only pins; an accepted unpinned exact entry does not itself reveal a tool. Unmatched entries reject atomically under the existing candidate-validation contract. No wildcards, fuzzy/cross-server selectors, automatic defaults or classification heuristics. An explicit broad default can affect a revealed write unless an exact patch overrides it; document that risk rather than filtering writes.

**Approved-contract supersession:** applying defaults/exact patches to revealed targets intentionally replaces METADATA-r7 R4/AC4's pin-only eligibility and unpinned-exclusion obligations (`.scratch/tool-metadata/spec.md:28,120`). Affected pin-only expectations in `cmd/mcp-bridge/serve_hybrid_metadata_defaults_test.go` must later be migrated to the renewed PR-R3/PR-AC4 contract, not silently retained, weakened or treated as an implementation defect. Preserve unaffected same-server isolation, built-in/generic independence, explicit opt-in behavior, precedence and strict validation. Requirements and design need renewed explicit checkpoints; old METADATA receipts do not authorize this change.

### 4.5 Runtime acceptance, projection reconciliation and admission
Use a short bridge coordination barrier shared by runtime acceptance handoff, projection commit and direct admission. It serializes the final accepted-generation check with projection commit and lease acquisition; it does not make storage and projections transactional. Keep storage/upstream I/O outside the projection lock. Runtime acceptance remains after its existing persistence step and before projection reconciliation.

Accepted-generation handoff records the accepted generation in the coordinator and preserves existing current.Store/retirement semantics. Later Published/reconciliation may prepare outside the barrier, then verifies it still targets the current accepted generation before swapping complete live projections. If a newer runtime has been accepted, discard the older prepared reconciliation rather than regressing state. All reload/refresh acceptance callers and session enrollment participate in this same ordering contract.

Between acceptance and reconciliation, a list may return the previous complete projection. A stale binding is not thereby executable: direct admission checks owner liveness, visible name and projection/runtime compatibility and acquires the existing runtime lease for that exact binding/schema/route tuple under the short barrier. If its generation is no longer admissible, reject using existing catalog-change/draining/error semantics without upstream dispatch. Never pair an old schema/binding with a separately loaded newer runtime. An already admitted call may finish on its ordinary lease; slow execution holds no publication lock.

For new enrollment, require §4.9's ordinary inbound admission, applicable SDK initialization checks and matching live incarnation. Derive baseline pins from the accepted generation and commit only while both that incarnation remains live and the generation remains current. Concurrent first relevant requests share the same incarnation and enroll one baseline; they must not replace a projection or erase interests another request already committed. If accepted generation changes during preparation, do not enroll a stale projection or silently expose a mixed baseline. Preserve existing cold-start/deferred-pin behavior. Reconciliation failure after acceptance cannot undo runtime acceptance or restore retired generations. Retain the last complete projection, reject stale direct admissions, expose failure through existing truthful protocol/status/diagnostic paths and do not falsely report successful reconciliation. A later normal accepted reconciliation may replace it; no new retry loop or storage transaction is introduced.

### 4.6 Discovery commit and F-01 ordering
Search/describe evaluates against accepted generation G and trusted owner incarnation O, resolved from the current request under §4.9 rather than an HTTP connection context. Prepare the full successful result, all target descriptor/binding changes, collision/metadata validation and response serialization before its projection commit. Empty success adds no interests. Invalid name/revision, failed evaluation or preparation failure adds none.

At commit, under the coordination barrier, require O still live, G still current and the prepared state not older than the owner's committed state. Merge concurrent successful discoveries against the current same-G interests so neither erases the other; recompute the complete projection delta from those interests. Do not silently retry evaluation or rebase results onto a different accepted generation. Generation/session invalidation uses existing finite failure semantics.

Commit interests and the complete immutable descriptor/binding projection, reconcile the prepared union registry, and only then release success. This applies to both search and describe, including mixed read/write results and pinned-target interest. A re-list after success observes that projection unless a later legitimate publication intervened. No network response can be treated as proof of client receipt.

Projection-precommit failure retains the previous projection and does not schedule a rejected-candidate signal. A rejected runtime candidate retains accepted runtime according to existing semantics; this says nothing about pre-rename versus post-rename disk bytes. Postcommit cancellation, response-write/disconnect or notification failure does not retract committed exposure. Repeating unchanged successful discovery is idempotent. Search/describe/list execute zero upstream tool operations.

### 4.7 Atomic pages and concrete opaque cursors
Middleware uses the entire immutable owner projection, sorted by the SDK-compatible exposed-name order, and constructs one page from it. Page size is the current effective configured positive SDK `PageSize`, if one is actually supplied at the existing server construction; otherwise use the public `mcp.DefaultPageSize=1000`. The supplied bundle does not establish a positive production setting, so this draft claims none. Add no new configuration option. A later controlled fixture may construct the existing SDK server with a positive PageSize to verify that branch without introducing production configuration. Do not paginate the union and then filter; no session page may silently drop reachable tools.

Select a stateless authenticated bridge cursor: fixed version, owner epoch, projection generation and next offset, authenticated with HMAC-SHA256 using one cryptographically random process-local secret. The owner epoch is unique and monotonic within that process. Cursor material is opaque, has no raw session ID, bearer, tool name or metadata, and is never logged. The process secret is transient, not externally configured or persisted. Secret initialization failure fails service setup through existing safe startup failure handling, rather than issuing unauthenticated cursors.

A concrete version-1 encoding is raw URL-safe base64 of 1 version byte, three unsigned 64-bit big-endian values (owner epoch, generation, next offset), and a 32-byte MAC: 57 decoded bytes/76 encoded characters. Authenticate the versioned body and reject noncanonical or wrong-sized input before using positions. Validate MAC in constant time, owner epoch, current generation, nonzero in-range continuation offset and valid page boundary. Emit `nextCursor` only when more descriptors remain. A page contains at most the effective page size; following valid cursors reaches every descriptor exactly once without omission or duplication. Empty/final pages have no next cursor. Replaying a cursor or running independent scans is supported while the projection generation is unchanged; there is no per-request cursor allocation table.

Capture the projection and validate the cursor against that same committed pointer at one linearization point. Serialize owned immutable descriptor values after releasing the lock. On any malformed, stale, cross-owner, retired-owner or invalid-position cursor, return public `jsonrpc.Error` with `jsonrpc.CodeInvalidParams` (-32602), finite message `invalid cursor`, no sensitive details and no partial list data. Do not expose MAC/epoch/generation mismatch diagnostics or silently restart.

A projection change invalidates earlier continuation even if the same bearer owns both sessions. No lock spans the client's inter-page interval and no historical projection is retained for cursor continuation. A page linearized before a later commit may still be delivered afterward; its next cursor then fails on continuation. This is immutable single-response consistency plus generation-validated continuation, not retained multi-page snapshot isolation.

### 4.8 Notifications and client limits

Coalescing, asynchronous delivery and broad notification fan-out are allowed. No exact one-notification-per-operation guarantee, synchronous send barrier or ordering relative to the discovery response is promised. A signal can describe a publication already superseded by a later one; re-list obtains the requesting session's current complete projection.

Hold no bridge lock across upstream I/O, network response write or notification delivery. Notification/response failure cannot undo publication. Unchanged discovery does not mutate registry solely to generate a signal. Generic dispatch remains conservative. The bridge guarantees explicit re-list, not immediate client re-listing, cache adoption, policy changes or Gemini prompt outcomes.
