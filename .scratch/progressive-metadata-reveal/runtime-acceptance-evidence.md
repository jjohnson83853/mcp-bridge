**E4 — Important durability qualification.** Store.Save validates/checksums/encodes an owned top-level snapshot copy (`internal/storage/store.go:201-230`). Publication writes and fsyncs a temporary file, closes it, renames it over the live snapshot, sets trusted, and only then returns directory-sync status (`internal/storage/store.go:262-288`). Therefore a directory-sync error can be returned **after the live path was replaced**. The blanket comment that any failed save preserves the old snapshot (`internal/storage/store.go:197-200`) is not proved by this implementation. This is a static control-flow finding, not an exercised filesystem failure. Do not promise durable rollback on every Persist error or silently repair storage in this feature.

**E5 — Observer is after acceptance, not a veto.** Refresh.runPass calls Runtime.Refresh before report, and report invokes Published only on successful returned assemblies (`internal/service/refresh.go:189-207`). Command wiring calls promptSurface.Published, then ToolSurface.Published, then the operating observer (`cmd/mcp-bridge/serve.go:201-205`). ToolSurface.Published returns no error, and descriptor preparation failure logs/rejects only that surface update (`internal/service/tools.go:115-170`). Thus its failure cannot reject the already stored runtime pointer or undo already completed persistence. Comments about retaining the previous published generation at `internal/service/tools.go:154-157` refer to the registry surface, not Runtime.Current.

**E6 — Registry mutation is sequential.** Published holds ToolSurface.mu, computes changes, prebuilds every descriptor, then individually removes old SDK tools and adds replacements while changing the bridge pin map (`internal/service/tools.go:119-180`). Unchanged bindings skip re-registration (`internal/service/tools.go:138-145`). Descriptor-build rejection happens before these SDK mutations. The bridge mutex serializes these writers; it does not itself enclose SDK list readers.

**E7 — Descriptor ownership is global in present wiring.** One ToolSurface holds one server and one pin map (`internal/service/tools.go:42-53,72-78`). The command constructs one MCP server, registers tools and prompts on it, and passes that server into one streamable handler (`cmd/mcp-bridge/serve.go:112-118,138-155`). These descriptors are not a per-client reveal set. The separate auth/session machinery is not evidence of session-local descriptor ownership. This slice makes no additional lifecycle claims about files outside its allowlist.

**E8 — Discovery does not currently publish descriptors.** Search captures an assembly, evaluates search and marshals/returns its response with no registry update (`internal/service/tools.go:463-488`). Describe checks revision/name against its captured assembly, derives its payload, conditionally includes pinned effective metadata, and marshals/returns success without registry mutation (`internal/service/tools.go:512-558,583-590`). Its success log precedes marshaling (`internal/service/tools.go:569-585`). Consequently neither current handler establishes reveal-before-success.

**E9 — Direct admission spans separate views.** callPinnedTool captures a pin from the registered map under ToolSurface.mu, releases it, independently reads Runtime.Current and optionally falls back to current pins (`internal/service/tools.go:209-224`). It validates the captured binding's input schema, then leases/dispatches through the independently captured assembly (`internal/service/tools.go:234-259`). This is not one atomic descriptor/binding/assembly capture.

**E10 — Existing lease retention.** Assembly.Acquire refuses unavailable or retired trackers and returns the exact server/client lease (`internal/service/reload.go:208-224`); Release is once-only (`internal/service/reload.go:248-261`). Retirement refuses new acquisition and runs close after the admitted leases drain (`internal/service/reload.go:274-317`). Carried clients retire the old tracker without closing the shared client; replaced clients close on drain (`internal/service/reload.go:732-754`). Retaining an Assembly pointer alone does not reserve permission to obtain a later lease after retirement.

**E11 — Cross-driver atomicity is not established.** Loop starts refresh and reload-watch drivers in separate goroutines (`internal/service/loop.go:162-171`); watch invokes Reload (`:181-194`), and refresh independently invokes Runtime.Refresh (`internal/service/refresh.go:189-197`). The observed build entry and publication contain no joint acceptance mutex/CAS (`internal/service/reload.go:373-425,600-616`). **[INFERENCE]** overlapping builds can use the same predecessor, and callbacks can arrive out of accepted-pointer order; ToolSurface.mu serializes callbacks but has no generation rejection check in `internal/service/tools.go:115-180`. An atomic pointer is not a serialized prepare/persist/registry transaction. No race was run or claimed.

## 4. DESIGN — FEASIBILITY FINDINGS, NOT A SELECTION

- **Infeasible as sufficient solutions:** leave void Published as the acceptance gate; rely on ToolSurface.mu alone for atomic tools/list; rely on debounce timing for post-commit notification; add revealed tools to the present shared server and call that session isolation; treat an acquired old Assembly pointer as an execution lease. E3/E5/E6/E7/E10 establish the respective missing boundaries.
- **Conditionally feasible for one list request:** all publication writers share a bridge write barrier and receiving tools/list holds its read side through SDK result construction; returned descriptor objects are never mutated. This hides intermediate SDK mutation states from participating readers. It does not solve pagination, notification delivery or accepted-runtime coordination.
- **Conditionally feasible acceptance integration:** complete fallible projection/descriptor/binding preparation before persistence and pointer acceptance, followed by a coordinated publication boundary that cannot reject one surface after accepting another. This requires explicit serialization with refresh/reload, session enrollment and lease admission; it is not achieved by changing the observer's return type after Store. E4's post-rename error semantics remain a separate acceptance-contract concern.
- **Candidate alternatives requiring missing proof:** an immutable per-session projection consumed through supported SDK middleware; or a fully prepared session-owned SDK registry with a supported swap/association seam. Neither is selected. A list-only filter without a matching direct-call visibility gate is insufficient. Replacing an SDK server for an existing session is not presumed supported. Pagination must preserve the existing wire contract; no new cursor or stale-cursor error is authorized here.
- **Notification alternatives remain conditional:** a supported outgoing barrier/coalescer, or supported automatic-notification suppression with exactly one post-commit scheduling owner, could provide a commit boundary. Do not assume either API exists until the supplied SDK excerpts establish it. Never add duplicate explicit notifications, hold publication locks across network I/O, or use sleeps as synchronization.
