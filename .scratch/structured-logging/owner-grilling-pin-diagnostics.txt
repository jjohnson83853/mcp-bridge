OWNER GRILLING — pin-resolution diagnostics
Session: 2026-11-11, /grilling (grill-me), project /home/opencode/projects/default/mcp-bridge
Feature: structured-logging. Scope set by the owner during this session: pin diagnostics only.
Answers below are the owner's, verbatim where quoted.

Q1: When a configured pin cannot resolve, should the bridge reject the entire catalog refresh, or publish the valid tools and report the unresolved pins?
A1: mandatory

Q2: Should one failed pass report every unresolved pin, or only the first?
A2: "I'm more interested in frilling on whether we have enough logging"

Q3: A refresh fails and the catalog stays empty. From logs alone - without metrics, /readyz, or another restart - must an operator identify every blocking pin and distinguish upstream discovery failure from tool-absent and from candidate publication failure?
A3: yes

Q4: Is reporting only the first blocking pin acceptable?
A4: no

Q5: When a refresh fails, must logs distinguish what remains usable (previous catalog retained with generation/tool count/age, versus no usable catalog)?
A5: yes

Q6: Must upstream failures identify the failing stage and cause, not just "discovery failed"?
A6: yes

Q7: Must logs show that a configuration edit actually reached the running process (revision, trigger, accepted or rejected)?
A7: yes

Q8: Must a successful refresh explicitly close the failure (completion record with revision, generation, counts, duration, recovery)?
A8: yes

Q9: If the same failure repeats every refresh interval, should every failed pass remain visible?
A9: yes

Q10: Must logs distinguish a stalled refresh from one waiting for its next scheduled run?
A10: yes

Q11: If discovery fails for a server, should its pins be reported as unverifiable rather than tool-missing?
A11: yes

Q12: What proves the logging is sufficient before we ship - independent reviewer reconstruction from captured logs?
A12: "independent review by myself."

Q13: Do you want captured logs from deliberately induced failures, or will you judge logs during normal deployment?
A13: no

Q14: When a mandatory pin is missing, must the log list the actual tool names discovered on that server?
A14: yes

Q15: Should failure logs include every discovered tool name, chunked across bounded records without silent truncation?
A15: yes

Q16: Should logging failures themselves be visible (encode failure or writer rejection surfaced, credential-free)?
A16: yes

Q17: Should routine successful refreshes log every server and tool name?
A17: no

Q18: Then what should a successful refresh log?

Q19: Must rejected reload logs identify the exact configuration location - file, property path, line and column - alongside every blocker?

Q20: If configuration passes validation but fails later during discovery or pin resolution, must logs still point to the originating YAML entry?
A20: yes

Q21: Should discovery retryability be explicit in failure logs (automatic retry scheduled versus configuration or credentials need correction, with next attempt time)?

A25: yes

A26: yes
