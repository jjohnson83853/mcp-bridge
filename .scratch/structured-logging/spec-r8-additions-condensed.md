For each affected server the actually discovered tool names are listed (affected servers only, never healthy servers), split across bounded records sharing the refresh correlation ID, server ID and chunk index/count, with no silent truncation. Every failed pass repeats its complete details — no deduplication, no reference to an earlier failure ID.
- R22 (owner rulings 6, 7, 11, 12, 14, 15): Logs alone are the diagnostic path: an operator identifies all blockers, the configuration revision used, and the catalog still being served without consulting metrics or `/readyz`. Every refresh pass emits start and outcome records sharing one correlation ID, stating the configuration revision, the trigger, and the next scheduled attempt. A failed pass distinguishes the retained catalog (generation, tool count, age) from no-usable-catalog/zero-upstream-tools, and distinguishes candidate counts from retained counts. A successful refresh emits an explicit completion summary with COUNTS ONLY — servers discovered, tools discovered, tools published, mandatory pins resolved out of total — and never per-server or per-tool listings. Start records make stalled-versus-waiting distinguishable (correlation ID + next attempt).
- R23 (owner rulings 8, 9): An upstream discovery failure names the failing stage — closed set `dns|connect|tls|auth|initialize|tools_list` — with a bounded cause category and the HTTP status or timeout value where applicable. The endpoint appears sanitized as scheme/host/port/path only; never credentials, headers, query strings, or bodies (R8). - R25 (owner rulings 16, 17): All pin/refresh diagnostics appear at DEFAULT log levels; no failure diagnostic is debug-only. Defects in the logging path itself are surfaced as a minimal credential-free fallback record rather than failing silently.
