## 2. REQUIREMENTS

**R1 — Compact index hits (AC1, AC2, AC7).** Each `search_tools` result row contains exactly the fields `tool_name`, `description`, `score` — nothing else. `tool_name` is the existing effective wire name (internal/service/tools.go:987–1003). `description` is bounded and one-line by construction, in two deterministic steps applied to the stored description at the wire choke point only (stored/embedded descriptions are never modified):
1. **Normalization (one-line, F1 mechanism):** every maximal run of one or more characters from the whitespace-control class W = {U+0020} ∪ {Unicode category Cc: U+0000–U+001F (CR, LF, TAB, other C0), U+007F–U+009F (DEL, C1)} ∪ {U+2028 (LINE SEPARATOR), U+2029 (PARAGRAPH SEPARATOR)} is replaced by a single space `" "`; leading/trailing spaces are then trimmed. After this step the emitted description can never contain a control character or a line break (N6: U+2028/U+2029 included).
2. **Bounding:** the JSON-encoded byte length of the normalized string (bytes it contributes to a marshaled JSON string body, excluding delimiting quotes) never exceeds 36. The encoded length is measured for every description — there is NO raw-byte fast path (N1): a description of 24 `"` is 24 raw bytes but 48 encoded bytes, exceeds the budget, and is truncated and marked. If the normalized description fits 36 encoded bytes it passes through unchanged with no marker. Otherwise truncation takes the longest rune-boundary-aligned prefix of the normalized string whose encoded length fits 36 − 3 bytes reserved for the marker, then appends the visible marker `…` (U+2026, 3 encoded bytes) exactly when any suffix was dropped; multi-byte UTF-8 sequences are never split; identical input yields byte-identical output. Quote/backslash/HTML-escape content inside the description passes through `json.Marshal` escaping unchanged (its wire cost is accounted in §4).

No schema content (`input_schema`/`output_schema` or any other schema-derived data) appears in any hit. `describe_tool` remains the only response path returning stored input/output schemas (unchanged; tools.go:507-538 and projection.go:367-430 keep consuming internal identity, never the pruned wire fields).

**R2 — Small enforced limits (AC3; scoped to valid operator configs).** Bridge-level compact-index caps `IndexTopKDefault=3` and `IndexTopKMax=4` (compile-time constants in internal/search, not operator config). Effective default = min(operator `default_top_k`, 3); effective caller-visible maximum = min(operator `max_top_k`, 4); no other transformation. This requirement applies to operator configs satisfying the existing `search.Config` invariant `TopKMax ≥ TopKDefault` (internal/search/search.go validate, enforced at every `DecodeRequest` after the caps clamp); for such configs the caps clamp always preserves default ≤ maximum: if d ≤ m, then min(d,3) ≤ min(m,4) (d ≤ 3 ⇒ result ≤ m when m < 4 and ≤ 4 otherwise; d > 3 ⇒ m ≥ d > 3 so min(m,4) = 4 ≥ 3). A request with `top_k` above the effective maximum is rejected by the existing strict path (`internal/search/search.go:150-171`, error `invalid_arguments` "top_k is outside the configured bounds") — never silently clamped. The advertised input schema's `top_k.default`/`maximum` (internal/catalog/schema.go:35-56) must equal the enforced effective values per surface, so the caller-visible maximum is small everywhere the tool is listed. Degenerate operator configs (`default_top_k > max_top_k`) remain out of scope for hardening, but the caps clamp changes which of them admit (N2): because `withDefaults` clamps before `validate`, a degenerate config admits a search exactly when min(d,3) ≤ min(m,4) — e.g. default 10/max 5 clamps to (3,4) and validates — while a config with `max_top_k < 3`, or any config where min(d,3) > min(m,4) (e.g. default 10/max 2 → (3,2)), still fails at the pre-existing validate step. No coherence guarantee is claimed or documented for degenerate configs; the load-time diagnostic and its tests are deferred to repo issue #165, whose premise that all degenerate configs fail every search is partly superseded by the clamp (the diagnostic itself remains needed).

**R3 — Root envelope and preserved mechanics (AC4, AC6).** Unchanged from r1/r2: root keeps `catalog_revision`, `mode`, `degraded_reasons` (tools.go:1008-1034); adds `match_count` — the number of ranked matching results before count clipping (= length of the fused pre-TopK population, search.go:421-433) — and `truncated` (`true`) at the root only when the matched population exceeds the returned result count; both fields absent when nothing was clipped (absence ⟺ `match_count == len(results)` and no truncation).
