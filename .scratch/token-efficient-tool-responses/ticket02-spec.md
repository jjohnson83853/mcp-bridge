## 2. REQUIREMENTS

**R1 — Compact index hits (AC1, AC2, AC7).** Each `search_tools` result row contains exactly the fields `tool_name`, `description`, `score` — nothing else. `tool_name` is the existing effective wire name (tools.go:987–1003). `description` is bounded: its JSON-encoded byte length (the bytes it contributes to a marshaled JSON string, excluding delimiting quotes) never exceeds 48; truncation takes the longest deterministic prefix of the stored description that fits 48 encoded bytes minus 3 bytes reserved for the marker, and appends the visible marker `…` (U+2026, 3 encoded bytes) exactly when any suffix was dropped; an already-fitting description passes through unchanged with no marker; multi-byte UTF-8 sequences are never split; identical input yields byte-identical output. No schema content (`input_schema`/`output_schema` or any other schema-derived data) appears in any hit. `describe_tool` remains the only response path returning stored input/output schemas (unchanged; tools.go:507-538 and projection.go:367-430 keep consuming internal identity, never the pruned wire fields).

**R2 — Small enforced limits (AC3).** Bridge-level compact-index caps `IndexTopKDefault=3` and `IndexTopKMax=4` (compile-time constants in internal/search, not operator config). Effective default = min(operator `default_top_k`, 3); effective caller-visible maximum = min(operator `max_top_k`, 4). Operator bounds stay 1..50 (internal/config/bounds.go:86 unchanged); existing configs (config.example.yaml:45-47, config.mcp-grafana-stack.yaml:30-32 setting 10/50) remain valid and effective 3/4. Operator knobs can only lower the effective values. A request with `top_k` above the effective maximum is rejected by the existing strict path (`internal/search/search.go:150-171`, error `invalid_arguments` "top_k is outside the configured bounds") — never silently clamped. The advertised input schema's `top_k.default`/`maximum` (internal/catalog/schema.go:35-56) must equal the enforced effective values per surface, so the caller-visible maximum is small everywhere the tool is listed.

**R3 — Root envelope and preserved mechanics (AC4, AC6).** Root keeps `catalog_revision`, `mode`, `degraded_reasons` (tools.go:1008-1034). Adds `match_count` — the number of ranked matching results before count clipping (= length of the fused pre-TopK population, search.go:421-433) — and `truncated` (`true`) at the root only when the matched population exceeds the returned result count; both fields are absent when nothing was clipped (absence ⟺ `match_count == len(results)` and no truncation). Ranking order and scores, `query`/`servers` filters, degradation reporting, catalog-revision mismatch behavior, strict decoding and the error taxonomy are unchanged except for the pruned hit fields and the R2 admission cap that AC3 mandates. `searchDiscoveryTargets` (tools.go:507-538) and `commitDiscovery` (projection.go:367-430) continue to consume the internal `search.Response` identity fields (ToolName/Server/UpstreamName/CatalogRevision/Pinned), never the pruned wire payload.

**R4 — Byte target and test matrix (AC5, AC8).** Documented response-size target: any `search_tools` response is at most 2048 bytes as measured by the established domain `len(json.Marshal(*mcp.CallToolResult))` (internal/service/result_measure.go:9-14, including the text/structured duplication), for responses at the effective maximum result count with long (≤64-char) wire names and budget-length descriptions. Feasibility arithmetic (section 4) shows worst-case margin ≥60 bytes. Test matrix per AC8: default count, cap rejection, truncation metadata, description bounding, serialized byte bound.

**R5 — Documentation (ticket Notes; AC9).** README.md and the live `search_tools` tool guidance (tools.go:96-105, builtin_guidance_test.go:15-83) document: the compact hit field set; the removals of per-hit `server`, `upstream_name`, `pinned`, `availability` (pinned inventory remains in the dynamic direct-first guidance sentence); the additions `match_count`/`truncated`; the effective default 3 / caller-visible maximum 4 and the clamp semantics over operator `default_top_k`/`max_top_k`; the 48-encoded-byte description budget with the `…` marker; the ≤2048-byte target; and that `describe_tool` is the only schema path. Config examples are unchanged and remain valid.

**Non-goals.** No session-exposure/search-fanout changes (ticket 03). No ticket-01 paging mechanics changes — except the test-fixture ceiling override in T3 required to keep the search-surface paging seam exercised (production ceilings unchanged). No ranking/filter-algorithm changes. No `describe_tool` behavior change. No upstream schema changes. No new operator config keys; the bridge caps are fixed constants with no validation surface (no operator input ⇒ no typed diagnostics required). No changelog (README is the documented surface for this change).

**[AUTO-DECISION] entries (persist to .scratch/token-efficient-tool-responses/decisions.md):**
- AD1: default 3 / caller-visible max 4. Why: the numbers that keep the AC5 worst-case envelope ≤2048 with ≥60-byte margin (§4 arithmetic); both are "small" per ticket. Consequence: operators above the caps get effective clamping; knobs remain meaningful only at/below the caps.
- AD2: description budget measured in JSON-encoded bytes (48), not raw characters. Why: `json.Marshal` HTML-escapes `<>&` and control chars (≤6 bytes each); a raw-character budget would let escape-heavy upstreams inflate hits ~6×. Consequence: escape-heavy descriptions yield fewer visible characters; the byte bound becomes airtight.
- AD3: marker `…` (U+2026, 3 encoded bytes), appended only when a suffix was dropped; budget includes the marker. Why: visible, single-token, bounded. Consequence: emitted description encoded length ≤48 always.
- AD4: `match_count`/`truncated` present only when clipped. Why: AC4's literal wording; minimal steady-state bytes; absence is well-defined (no clipping). Consequence: clients treat absence as `match_count==len(results)`.
- AD5: min-clamp inside `search.Config.withDefaults` (single function shared by `DecodeRequest`, `NewSearcher`, and the new `EffectiveBounds` accessor) instead of tightening operator bounds. Why: preserves existing 10/50 config validity (compatibility constraint); a configurable cap would let operators defeat the token budget; the ticket calls for a "hard cap". Consequence: no new config key, no validation/diagnostic surface; a previously-invalid default>max config can become valid post-clamp (previously it broke every search at validate time — improvement, documented).
- AD6: per-hit `server`/`upstream_name`/`pinned`/`availability` removed. Why: AC1 says "only … the minimum fields required to invoke it"; call_tool needs only `tool_name` (+ optional root-level catalog_revision); pinned inventory already lives in the dynamic guidance (tools.go:96-105). Consequence: client-visible removals, documented per R5; internal identity untouched for discovery.
- AD7: `SearchToolsInputSchema(topKDefault, topKMax int)` parameterized; constants `TopKDefault`/`TopKMaximum` removed; effective values computed once per surface (`cfg.Search.EffectiveBounds()` at `NewToolSurface`) and threaded through `renderBuiltinDescriptors`/`prepareProjection`/`preparePinProjection`. Why: advertised maximum must equal enforced maximum on every tools/list surface. Consequence: bounded signature ripple (3 production call sites + tests).
- AD8: search-branch fixture in discovery_paging_test.go lowers `DeliveryCeilingBytes` to 1024 (preview 512 unchanged) and sizes the fixture to a max-count compact response. Why: compaction makes search unpaging at the shared 8192 fixture ceiling, which would strand ticket-01's paging-seam coverage for search; production ceilings unchanged. Consequence: fixture-only; the search paging path stays regression-covered.

## 4. DESIGN

**Selected approach:** minimal projection change — the search engine stays authoritative; the service layer compacts at the single wire choke point (`searchPayload`); bounds are enforced once in the search package and mirrored into the advertised schema; no new abstractions.

**Components and contracts:**
1. internal/search — new constants `IndexTopKDefault = 3`, `IndexTopKMax = 4`; `withDefaults` clamps `TopKDefault`/`TopKMax` to the caps after zero-fill (ordering preserved by min monotonicity; `validate` unchanged and runs after clamp in `DecodeRequest`); new exported `func (c Config) EffectiveBounds() (topKDefault, topKMax int)` returning the clamped values; `Response` gains `MatchCount int` set to `len(fused)` in `Search` before slicing. `Result` struct, ranking, fusion, filters, degradation, caching: unchanged.
2. internal/catalog — `SearchToolsInputSchema(topKDefault, topKMax int)`; `top_k.default/maximum` take the parameters; `TopKDefault`/`TopKMaximum` constants removed; `QueryMaxLength`, `ServerFilterMax` and all other schemas unchanged.
3. internal/service — `NewToolSurface` computes and stores `searchTopKDefault`/`searchTopKMax` once via `cfg.Search.EffectiveBounds()`; `renderBuiltinDescriptors(resolvedPins []core.ResolvedPin, topKDefault, topKMax int)` passes them to the schema; `prepareProjection`/`preparePinProjection` gain the two bounds parameters; ToolSurface call sites (tools.go:213, projection.go:417 commitDiscovery, projection.go:943 publishProjection, session_exposure.go:217) pass the stored values. `searchPayload` emits hits `{"description": bounded, "score": score, "tool_name": effectiveWireName(...)}` (alphabetical key order preserved) and, only when `response.MatchCount > len(response.Results)`, root `"match_count"` and `"truncated": true`. New unexported `searchDescriptionMaxBytes = 48`, marker const, and a deterministic truncation helper beside `searchPayload` (longest rune-prefix whose JSON encoding fits 48−3 bytes when truncating; no marker when the source already fits; never splits UTF-8). Guidance strings in tools.go:96-105 gain the compact-index sentence; pinned-name inventory sentence unchanged.
4. Wire contract (response root): `catalog_revision` (64-hex, unchanged), `mode`, `degraded_reasons`, `results[]`, and conditionally `match_count` (integer, pre-clip matched population), `truncated` (bool, always `true` when present). Hit: `description` (string, ≤48 encoded bytes incl. marker), `score` (float64, unrounded — AC6), `tool_name` (string, ≤64 chars).

**Byte arithmetic (AC5 feasibility, worst case):** envelope = 4 hits (effective max), 64-char wire names, 48-encoded-byte descriptions (incl. marker), worst realistic score `"0.00819672131147541"` (19 chars — the actual fixture score at discovery_paging_test.go:95), `mode:"keyword"` + one 26-char reason (`embed_provider_unavailable`; the degradation switch is exclusive, so one reason max), clipped with 5-digit `match_count`:
- root = 202 bytes; hit = 42+64+48+19 = 173; 4 hits + 3 commas = 695; payload = 897.
- duplicate text copy = payload + 60 quote-escape bytes (root 20 + 10/hit quotes, doubled in the escaped string); structured copy = 897; wrapper ≈ 61.
- **Total ≈ 61 + 957 + 897 = 1915 ≤ 2048 (margin 133).** Exact-max unclipped ≈ 1797; default 3-hit response ≈ 1479. Every variable is bounded (name ≤64 by `effectiveWireName`, description ≤48 encoded by AD2, score shortest-round-trip ≤20 chars, one reason, 5-digit count), so the bound holds for all responses at ≤4 results, not just the tested envelope.

**Compatibility/security/failure behavior:** no secrets or payloads in the change; descriptions come from upstream catalogs and are already validated at ingestion (max_description_bytes); the truncation helper is the only new string handling. Error taxonomy unchanged: above-cap `top_k` and out-of-range values reuse the existing `invalid_arguments` record; catalog-revision and filter behavior byte-identical. The behavior change is response shape only; no concurrency or lifecycle change (response construction is per-request, no shared mutable state added; `MatchCount` is set per-Search).

**W09E shared review-risk matrix (candidate-bound):** Lifecycle — no new state transitions; MatchCount set per Search, consumed per payload; no restart/reload interaction beyond AD7 (see §9 risk 2). Shared state — no new writer; single choke point; no read-modify-commit. Contract — R→AC→T complete (§5/§6); verification noncontradictory (AC3 cap is scoped out of AC6's "unchanged" set, §9). Authority — no new owner ask; AC1–AC8 preserved; AC9 adds coverage of the ticket's own Notes. Observability — §7 with justified exceptions.
