## 1. STATUS
- Spec ID/revision: token-eff05-spec, revision r1 (bootstrap; no prior revision). DRAFT, corrected pre-review (editorial T-renumbering + T3 event-registration obligation; no R/AC changes).
- Objective: For exactly two allowlisted operations — `portainer__EndpointList` and Docker Engine `/containers/json` reached through `portainer__docker_proxy` — return a compact default field projection by default, disclose it in the response, keep explicit full opt-in and custom field selection working, and keep every delivered or paged result bounded by ticket 01's 8192-byte ceiling.
- Benefit statement (R3, informational only, no numeric AC): with ticket 01's ceiling landed, a full `/containers/json` result is 110237 bytes = 18 retrieval pages (`total_bytes: 110237` observed) and EndpointList is 25128 bytes (~4 pages). A pre-known identity/state projection (~9001 characters in the observed select experiment, ≈1.5 pages) reduces reconstruction to 1–2 pages. This is rationale, not an acceptance target.

## 2. REQUIREMENTS
- R1 (scope): Exactly the two observed operations are allowlisted: (a) server `portainer`, upstream tool name `EndpointList`; (b) server `portainer`, upstream tool name `docker_proxy`, operation discriminator `path == "/containers/json"` (exact string match). Proxmox (`proxmox__get_containers`) and OPNsense (`opn_list_*`) entries are EXCLUDED: the ticket makes them conditional on inspected stored schemas plus recorded default fields, and their decisive schemas/payload fields were not captured in the evidence bundle. This exclusion does not weaken AC1–AC7: AC1–AC3, AC5–AC7 are defined only over allowlisted entries and their fixtures (all of which exist for the two included entries), and AC4 (unaffected neighbors) is actually strengthened by more unallowlisted tools remaining untouched. Including them later is optional scope under a new owner decision, not a task here.
- R2 (default projection + disclosure): When no explicit projection request is present and an allowlist entry matches, the bridge replaces the upstream list payload with the entry's default projection and states in the response that a projection was applied, which fields it used, and which entry matched. The response must never present projected objects as the upstream's full shape.
- R3 (full opt-in): A caller-requested full response returns the upstream's unprojected objects unchanged (bridge does not transform them), still subject to ticket 01's delivery ceiling, retention and paging. This is not an unbounded escape hatch.
- R4 (custom selection + precedence): A caller-supplied field selection overrides the default projection, selects raw upstream top-level item keys copied verbatim, and rejects unknown fields deterministically (no silently narrowed payload). Precedence: absent request → default (if entry matches); `projection.full: true` → no bridge projection; `projection.fields` (1–16 unique strings) → custom selection (allowlisted entries only). `full` and `fields` together → deterministic invalid-arguments rejection.
- R5 (allowlist discipline): Entries are explicit identities (server id + upstream raw tool name + operation discriminator), never name patterns, substrings or provider heuristics. Each entry is justified by its captured stored schema (section 3/4). Unrelated Docker API paths (`/images/json`, `/containers/{id}/json`, ...) are never projected.
- R6 (safe degradation): Upstream tool errors, empty lists, non-list payloads, list items missing all default fields, and upstream shape changes must not silently drop fields: the bridge either applies the projection faithfully (disclosed) or passes the full upstream payload through unchanged with a disclosed, logged, counted skip reason. Skip/reject signals must be registerable events that actually reach the log lane (the closed `eventMessage` vocabulary drops unregistered event names at runtime), so the disclosure, warn record and counter are all observable. No partial payloads masquerading as complete projections.
- R7 (non-interference): Tools that are not allowlisted — including similarly named tools on other servers and the same proxy tool on other paths — behave byte-identically to today when no explicit projection request is sent; the outer envelope gains no `projection` key for them.
- Non-goals: no Proxmox/OPNsense entries; no new config surface (allowlist is code-level); no bridge-side JMESPath implementation; no new paging/retention mechanism (reuses `boundedCallToolResult`/`deliverBoundedResult`); no numeric performance AC; no default-projection application to `search_tools`/`describe_tool` results; no change to session-projection (`projection.go`) semantics — the new concept is named field projection and must not be conflated with the existing session-projection term in code or docs.

## 4. DESIGN
Selected approach — smallest boring seam reuse: a pure, dependency-free field-projection engine in a new package-private file `internal/service/field_projection.go`, invoked from `callTool` between `decodeUpstreamResult` (tools.go:1119) and the `payload`/`result` construction, before `t.boundedCallToolResult`. Over-ceiling results (full opt-in included) then flow through the EXISTING `deliverBoundedResult` paging path unchanged — no paging re-implementation, ticket 01's ceiling and `retrieve_result` retrieval fully preserved (R3).
Components and contracts (interfaces, no code here):
- C1 Allowlist table (field_projection.go): ordered static entries, each `{serverID string, rawName string, discriminator}` where discriminator is `wholeTool` for EndpointList and `pathEquals("/containers/json")` for docker_proxy; each carries `defaultFields []string` (endpoint entry: Id, Name, Type, Status, GroupID; container entry: Id, Name←Names[0], State, Image) and a stable `entryID` string for disclosure (e.g. `portainer.EndpointList`, `portainer.docker_proxy /containers/json`). Matching is exact identity only (R5); a non-match returns ok=false with zero allocation beyond the lookup.
- C2 Projection request (call_tool wire): optional `projection` object as specified in the AUTO-DECISIONs; validation happens in callTool's admission (decodeStrict on the extended wire struct + `CallToolInputSchema` in catalog/schema.go gains the `projection` property), producing either a structured request value or a deterministic invalid-arguments rejection before dispatch (for malformed shapes) or after dispatch (for payload-relative unknown fields).
- C3 Projection engine (field_projection.go): input = decoded upstream `mcp.CallToolResult`, matched entry, projection request; output = (possibly transformed) result + decision {outcome: applied|skipped|rejected, mode: default|fields|full, entryID, fields, reason}. Unwrap rules per E2/E3 + ASSUMPTIONS: locate the list document in the first text block by (a) direct JSON list parse, else (b) `{"result": "<string>"}` wrapper whose inner string parses as a JSON list; when structured content mirrors the wrapper shape it is re-derived from the same projected list, otherwise left untouched and disclosed. Tool-reported errors (`IsError`) are never projected (R6). Transformed bytes replace only the upstream payload; envelope fields (`server`, `tool_name`, `request_id`, content block classes, `isError`) are untouched.
- C4 Disclosure (callTool payload): when the caller sent a projection request or an entry matched, the outer envelope gains `"projection": {applied: bool, entry: <entryID>, mode: <default|fields|full>, fields: [...], reason?: <closed enum full_requested|payload_shape_unexpected|payload_unparseable|item_shape_unexpected>}`; when nothing was requested and no entry matched, the envelope is byte-identical to today (R7). The response thus always distinguishes projected from upstream shape (AC1/R2).
- C5 Rejection path: unknown-field and conflict rejections return the existing fixed, payload-free `invalid_arguments`-class error result (repo idiom: the rejection message never quotes submitted values), plus the C7 signals.
- C6 Composition with upstream `select`: per AUTO-DECISION — `fields`+`select` rejected; `full`+`select` = bridge no-op; default projection only applies when `select` is absent (upstream select output does not carry the raw item keys the defaults reference).
- C7 Observability hooks: new counter `bridge_projection_total{server, tool, outcome}` (outcome ∈ applied|skipped|rejected; labels bounded: validated server id, allowlisted rawName only, closed outcome) registered in `observe.Metrics` alongside `bridge_results_paged_total`; two new log events `projection_skipped` (`call_tool`, warn/degraded, reason enum) and `projection_rejected` (`call_tool`, warn/denied, reason enum) — both must be REGISTERED in `internal/observe/log.go` `eventMessage` (E10) or they are dropped at runtime as vocabulary violations — plus their pinned rows in docs/logging-contract.md, reusing existing fields `tool`, `server`, `count` plus one new union field `projection_reason` (closed enum). Applied projections log nothing (avoid noisy duplicates; response disclosure carries them).
- Compatibility/security/failure behavior: no new untrusted-input surface beyond `fields` strings, which are validated, never echoed into error messages or logs (count only), and never used in any query; projection cannot exceed the upstream payload it copies; malformed JSON anywhere falls back to pass-through; concurrent sessions share only the immutable allowlist (no new shared mutable state); result-store ownership/paging unchanged.
- W09E application (risk evidence + counterexamples per surface):
  - Lifecycle: producers = callTool dispatch; consumers = bounded delivery/paging/`retrieve_result`; no new lifecycle transitions; counterexample considered — projection applied after paging would page projected bytes while the handle retains unprojected bytes; rejected by ordering (projection strictly before `boundedCallToolResult`, so stored bytes are the delivered bytes).
  - Shared state: writers = none new (static allowlist; per-request local transform); counterexample — a mutable allowlist updated on reload could race an in-flight call; eliminated by making the table immutable process state.
  - Contract: R1–R7 ↔ AC1–AC7 all covered with distinct oracles (section 5/6); counterexample — projecting `search_tools` results would break discovery contracts; excluded by scoping the hook to callTool only.
  - Authority: no owner stop crossed; scope is exactly ticket #119's READY envelope (refinement R1–R3); no new approval needed; Proxmox/OPNsense exclusion preserves the conditional scope rather than widening it.
  - Observability: skip/reject visibility bound to AC6 verification in section 7; counterexamples — silently swallowing an unparseable wrapper would hide a live no-op (countered by warn event + counter + disclosed `applied:false`), and documenting an event without registering it in `eventMessage` would emit only `log_vocabulary_violation` (countered by the T3 registration deliverable and render test, E10).
  - Repair closure: root invariant is "never emit a projection that is not fully disclosed and never drop fields silently" — carried across all clauses (defaults, custom selection, errors, empty, shape change) and fixtures, not just one test.
- Alternatives considered and rejected: config-driven allowlist (fingerprint churn, more code than the two-entry need justifies); bridge-side JMESPath (duplicates upstream capability); projecting at the inbound edge (wrong layer — tool identity and args live at dispatch).
