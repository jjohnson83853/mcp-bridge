# 02: Trace successful MCP operations through backend execution

**What to build:** Operators can follow a successful MCP initialize/list/call flow from its HTTP request through the decoded MCP operation and any actual backend execution. Records name the admitted tool/configured backend and measure each boundary independently, without relying on public client IDs.

**Blocked by:** 01 — HTTP request diagnostics and precise admission failures.

Status: complete

Type: task

Source: Logging observability specification, revision LOG-OBS-r4 (supersedes the original r1 source reference; approved ticket scope and dependencies unchanged). Coverage: successful/supported-method portions of AC2, AC4, AC5 and AC8; relevant AC14–AC22 and AC24. Ticket publication approval does not authorize implementation; applicable project gates still apply.

- [ ] Before production edits, establish the pinned SDK's decoded receiving/terminal observation hooks, per-operation context lifetime, notification semantics and required response-writer interfaces from current evidence. Verify actual transport/session lifecycle assumptions. If the required context/outcome observation cannot be achieved without changing protocol behavior, stop affected work for planner review rather than adding a second parser or silently dropping acceptance. Include any narrowly necessary preparation in this working slice; do not deliver an unused observation abstraction.
- [ ] Real initialize, tools/list, tools/call and supported prompt flows report the finite decoded method and message kind defined by the spec. Notifications do not acquire fabricated responses. Classification observes existing protocol handling rather than parsing a second authoritative stream or trusting a truncated body prefix. Existing metrics retain their original method vocabulary.
- [ ] Each HTTP request has a server-generated internal request ID, each decoded operation a distinct operation ID, and each actual admitted backend dispatch a distinct backend-call ID. Parent IDs propagate through operation context. Multiple operations on a transport have distinct child IDs; no global caller-ID-indexed registry is introduced. Entropy failure uses the defined unavailable state, never a caller ID fallback.
- [ ] HTTP, MCP and backend terminal records report their own nonnegative durations and independent outcomes. Successful transport is not documented as proof of successful execution. Exactly one record is emitted per actual boundary; local work and rejected calls do not manufacture backend attempts. Preserve existing retry behavior rather than adding retries.
- [ ] Identities come from the registered public tool table and successfully admitted current catalog binding/configuration, using immutable generation-scoped approval sets and the spec's length/character bounds. Merely syntax-valid submitted names, stale or nonexistent identities and arbitrary upstream metadata are not approved log values. Configured identities remain useful metadata, not HMAC aliases; document that intentionally approved identifiers must not contain secrets.
- [ ] Preserve public X-Request-ID behavior, JSON-RPC IDs, envelope IDs, content, structured wrapper and isError. The new internal chain neither replaces nor emits caller/session identifiers. Required writer interfaces, flushing and operation context remain intact.
- [ ] The existing real HTTP/MCP harness and local fake upstreams prove the complete successful chain and actual production wiring. Captured records pass finite field/type validation; synthetic secrets in submitted identities, client IDs, headers and arguments never appear. Existing configuration diagnostics, metrics, session/reload and public-response regressions remain unchanged.

Retain deterministic RED/GREEN evidence for the new observable behavior, smoke the actual local initialize/list/call path, run focused/full-suite checks with at least 90% full-suite source-line coverage, and complete applicable code/Go/security review.
